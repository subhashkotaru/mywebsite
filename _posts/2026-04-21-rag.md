## Overview
{: #overview}

[RAG](https://arxiv.org/abs/2005.11401) (Lewis et al. 2020) enhances LLMs by conditioning generation on evidence retrieved from an external corpus at inference time. Instead of encoding all world knowledge into model weights at training time — a static, expensive, and lossy process — RAG separates *knowledge storage* (the index) from *knowledge retrieval* (the retriever) from *reasoning* (the generator).

The core intuition: a model that can look things up doesn't need to memorise them.

**When RAG is the right choice:**
- Knowledge is dynamic (updated more frequently than training cadence)
- Knowledge is proprietary (can't be in public training data)
- Traceability is required (answers must cite evidence)
- Knowledge domain is too large to fine-tune into weights economically

### Pipeline Architecture
{: #pipeline}

```
Documents
    ↓  [Ingestion]
Parse → Chunk → Embed → Index → Vector DB
                                    ↓
Query ─→ [Query processing] ─→ Retrieval (lexical + dense + re-rank)
                                    ↓
                            Context assembly
                                    ↓
                            LLM generation → Response + citations
```

Three main stages:

| Stage | Responsibility | Key decisions |
|---|---|---|
| **Ingestion** | Parse, chunk, embed, index documents | Chunk size, embedding model, index type |
| **Retrieval** | Select relevant context for a query | Sparse vs. dense vs. hybrid, K, re-ranker |
| **Generation** | Synthesise response from context | Prompt structure, citation format, faithfulness |

### RAG vs. Fine-Tuning
{: #rag-vs-finetuning}

| Dimension | RAG | Fine-Tuning |
|---|---|---|
| **Knowledge updates** | Index swap; no retraining | Full or LoRA retraining required |
| **Knowledge scope** | Arbitrarily large external corpus | Bounded by training data size |
| **Traceability** | Cites retrieved chunks | Opaque; no source attribution |
| **Labelled data needed** | Minimal (retrieval tuning optional) | Requires task-specific examples |
| **Stylistic adaptation** | Poor — generator style is fixed | Strong — tone, vocabulary, format |
| **Latency** | +retrieval cost per query | Same as base model |

**Recommendation:** start with RAG for knowledge access; add fine-tuning for stylistic adaptation. The two are composable — retrieval-augmented fine-tuning (RAFT) trains the model to reason over retrieved context in domain-specific ways.

### RAG vs. Long Context
{: #rag-vs-long-context}

Modern 1M-token context windows raise the question: why retrieve at all?

| Dimension | RAG | Long Context |
|---|---|---|
| **Corpus size** | Billions of documents | Bounded by context window |
| **Compute per query** | Sub-linear (retrieval + short context) | Linear in total document length |
| **Knowledge updates** | Index swap | Re-encode entire corpus |
| **Lost-in-the-middle** | Avoided — only relevant chunks are present | Real problem; central content overlooked |
| **Exact recall** | May miss if chunking splits evidence | Lossless if fits in window |

Long context is best for fixed, bounded corpora (a book, a codebase) where you can afford the compute. RAG is better for large, dynamic, or access-controlled corpora.

## Ingestion
{: #ingestion}

### Chunking Strategies
{: #chunking}

Chunking divides source documents into retrieval units. The right strategy depends on document structure, embedding model input limits, and the retrieval granularity the task requires.

**Fixed-size chunking.** Split by token count (e.g., 256 tokens) with optional overlap. Simple and fast; chunk boundaries often cut semantic units mid-sentence.

```
chunk_size = 256 tokens
overlap = 32 tokens  ← prevents boundary loss
```

**Sentence splitting.** Use NLTK or spaCy tokenisers to split at sentence boundaries. Preserves semantic completeness; chunk sizes vary, which complicates batching.

**Recursive chunking.** Hierarchical splitting with multiple separator levels: paragraphs → sentences → words. Respects document structure better than fixed-size.

**Structure-based.** Parse Markdown headers, HTML tags, or LaTeX environments to split at natural document boundaries. Best for structured documents.

**Semantic chunking.** Group sentences by cosine similarity; merge until similarity falls below a threshold. Produces topically coherent chunks at the cost of variable lengths and higher ingestion compute.

**Late chunking** (JinaAI). Embed the full document first using the embedding model's full context window, then chunk the resulting *token-level representations* rather than the raw text. Preserves global context within each chunk's embedding — a chunk that says "she" now knows who "she" refers to from the document context.

**Chunk size selection heuristics:**

| Factor | Smaller chunks | Larger chunks |
|---|---|---|
| Query granularity | Precise factual lookup | Broad conceptual questions |
| Embedding model input limit | Must not exceed | Must not exceed |
| Retrieval noise | Lower (more precise) | Higher |
| Context completeness | Risk of missing surrounding info | Better completeness |
| Storage cost | Higher (more embeddings) | Lower |

In practice: validate empirically with your retrieval metrics. A common starting point is 256–512 tokens with 10–15% overlap for general Q&A.

**Parent-child (small-to-large) chunking.** Store small chunks for retrieval precision; return the parent (larger) chunk for generation. Retrieval finds the needle; generation gets the full sentence.

**Auto-merging / hierarchical chunking.** Index documents at multiple granularities. When a threshold fraction of sibling child chunks are retrieved for the same parent, replace them with the parent chunk in context. Reduces redundant overlapping context.

### Embedding Models
{: #embedding-models}

Embedding models map text to dense vectors in a shared semantic space. Similarity in this space proxies relevance.

**Sentence-BERT (SBERT)** ([Reimers & Gurevych 2019](https://arxiv.org/abs/1908.10084))

Addresses BERT's O(n²) cross-encoder complexity for similarity tasks. Uses Siamese/triplet networks to produce independently computed embeddings — enabling O(n) pre-computation of document vectors.

Architecture: BERT encoder → mean pooling over token embeddings → fixed-size sentence vector.

Training objectives:

| Objective | Formula | Use case |
|---|---|---|
| **Classification** | Concatenate $(u, v, \|u-v\|)$ → linear layer | NLI-style data |
| **Regression** | MSE between $\cos(u,v)$ and human score | STS benchmarks |
| **Triplet loss** | $\max(0,\; \|u - u^+\|^2 - \|u - u^-\|^2 + \epsilon)$ | Anchor-positive-negative triplets |
| **MNRL** | $-\log\frac{e^{\cos(q,d^+)}}{\sum_j e^{\cos(q,d_j)}}$ | In-batch negatives; most efficient |

**Model selection.** Use the [MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard) for standardised comparison across retrieval, STS, and classification tasks. Key tradeoffs:

| Model class | Dimension | Speed | Quality |
|---|---|---|---|
| Small (MiniLM, e5-small) | 384 | Fast | Good for symmetric queries |
| Medium (BGE-base, e5-base) | 768 | Medium | Strong general purpose |
| Large (e5-large, GTE-large) | 1024+ | Slow | Best accuracy |
| API (OpenAI text-embedding-3) | 1536/3072 | API latency | Top-tier, no self-hosting |

**Sparse vs. dense embeddings:**

| Type | Representation | Strengths | Weaknesses |
|---|---|---|---|
| **Sparse (TF-IDF, BM25)** | High-dim bag of words | Exact keyword match, fast, interpretable | Vocabulary mismatch; no paraphrase understanding |
| **Dense (SBERT, BGE)** | Low-dim continuous | Semantic similarity, paraphrase robust | Misses rare terms; slow to index |
| **Learned sparse (SPLADE)** | Sparse but learned | Combines both; keyword + semantic | Higher training cost |

### Indexing
{: #indexing}

**Exact nearest neighbour** — brute-force dot product or cosine similarity. Correct but O(n) per query; only viable for small corpora (<100K vectors).

**Approximate Nearest Neighbours (ANN)** — trades small recall loss for orders-of-magnitude latency improvement. Standard for production:

| Algorithm | Mechanism | Strengths | Weaknesses |
|---|---|---|---|
| **HNSW** | Hierarchical proximity graph | High recall, low latency, dynamic insertion | High memory (~100 bytes/vector) |
| **IVF** | Inverted file + cluster centroid search | Scalable, low memory | Recall drops if query falls between clusters |
| **IVF-PQ** | IVF + product quantisation | Best memory efficiency | Accuracy loss from quantisation |
| **ScaNN** | Asymmetric quantisation + tree search | Google-scale performance | Complex tuning |

Use [ANN-Benchmarks](https://ann-benchmarks.com/) for standardised recall-latency comparisons.

**Vector databases** handle ANN indexing plus metadata storage, filtering, and hybrid search. Major options: Pinecone, Weaviate, Qdrant, Milvus, pgvector (Postgres extension). Key selection dimensions: hybrid search support, metadata filtering, replication, query latency SLAs, and managed vs. self-hosted.

## Retrieval
{: #retrieval}

### Sparse (Lexical) Retrieval
{: #sparse}

**TF-IDF:**

$$\text{TF-IDF}(t, d) = \text{TF}(t,d) \cdot \log\!\frac{N}{\text{DF}(t)}$$

Weights a term by how often it appears in the document, penalised by how common it is across the corpus. Simple and interpretable; no learning required.

**BM25** (dominant lexical method):

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d)\,(k_1 + 1)}{f(t,d) + k_1\!\left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

- $k_1 \in [1.2, 2.0]$: controls TF saturation (diminishing returns on repeated terms)
- $b \approx 0.75$: controls document-length normalisation

BM25 is the de facto baseline for sparse retrieval. It handles long queries well and is exact (deterministic, no ANN approximation). Strong for: technical identifiers, code, named entities, exact phrase matching.

Limitations: vocabulary mismatch (query says "automobile", document says "car"), no semantic understanding, poor paraphrase handling.

**SPLADE** ([Formal et al. 2021](https://arxiv.org/abs/2107.05720)): learned sparse representation trained with FLOPS regularisation to encourage sparsity. Produces sparse vectors that cover vocabulary expansion — effectively learns BM25-like representations with semantic understanding. Strong performance, but requires training and index rebuild when model is updated.

### Dense (Semantic) Retrieval
{: #dense}

Embed query and documents with the same model; retrieve by cosine similarity:

$$\text{cosine\_sim}(q, d) = \frac{\vec{q} \cdot \vec{d}}{|\vec{q}||\vec{d}|}$$

**Training: Dense Passage Retrieval (DPR)**

Uses contrastive (in-batch negative) loss:

$$\mathcal{L} = -\log\frac{e^{\text{sim}(q,\, d^+)}}{e^{\text{sim}(q,\, d^+)} + \sum_j e^{\text{sim}(q,\, d^-_j)}}$$

Where $d^+$ is the positive passage and $d^-_j$ are negatives (other questions' positives in the batch). Hard negative mining — using passages that BM25 ranks highly but are actually wrong answers — dramatically improves training quality.

**Retrieval variants:**

| Variant | What's indexed | What's retrieved | Best for |
|---|---|---|---|
| **Standard** | Chunks | Same chunks | General Q&A |
| **Sentence-window** | Sentences | Sentence + surrounding context | Precise retrieval, rich context |
| **Small-to-large** | Small chunks | Parent chunk | Precision + completeness |
| **Proposition retrieval** | Atomic propositions | Proposition + source | Highly factual queries |
| **Contextual** (Anthropic) | Chunks + prepended context | Contextualised chunk | Reduces failed retrievals by 49% |

**Contextual Retrieval** (Anthropic, 2024): before embedding, prepend a short LLM-generated contextual description to each chunk explaining its role in the full document. A chunk that says "The temperature was recorded at 37°C" becomes "This chunk is from a study on fever thresholds in ICU patients. The temperature was recorded at 37°C." Reduces failed retrievals by 49% by enriching the embedding with document-level semantics.

### Hybrid Retrieval
{: #hybrid}

Neither sparse nor dense retrieval dominates universally. Hybrid combines both signals:

**Linear score fusion:**

$$\text{score}(d) = \alpha \cdot \text{BM25}(d) + (1-\alpha) \cdot \text{sim\_dense}(d)$$

$\alpha$ is tuned on a validation set; typically $\alpha \approx 0.3$–$0.5$.

**Reciprocal Rank Fusion (RRF)** — rank-based; insensitive to score scale differences:

$$\text{RRF}(d) = \sum_i \frac{1}{k + \text{rank}_i(d)}, \quad k = 60$$

Documents ranked well by multiple retrievers get boosted. $k=60$ is the standard smoothing constant. RRF is preferred over linear fusion when the two score distributions are incompatible (different scales, different sparsity).

**Standard production pattern:**

```
Query
├── BM25 → top-K₁ candidates (K₁ ∈ [100, 1000])
└── Dense ANN → top-K₂ candidates
        ↓
   Merge + deduplicate
        ↓
   Cross-encoder re-ranker → top-K₃ (K₃ ∈ [5, 20])
        ↓
   Context assembly → LLM
```

The first stage is cheap and high-recall; the second stage is expensive but high-precision.

### Re-Ranking
{: #reranking}

Re-rankers take a candidate set from the retriever and re-score each document against the query with a more powerful model.

**Bi-encoder re-ranker:** same architecture as the retriever — fast but limited by fixed embeddings.

**Cross-encoder re-ranker:** concatenates `[CLS] query [SEP] document [SEP]` and outputs a relevance score via full attention over both. Much more accurate (captures token-level query-document interactions); but O(K × query_length × doc_length) — only viable for small K (≤100 candidates).

Popular cross-encoders: `cross-encoder/ms-marco-MiniLM-L-6-v2` (fast), `bge-reranker-large` (accurate).

**Listwise re-rankers:** encoder-decoder models (T5/FiD-style) that score the full ranked list jointly. Better global coherence but expensive.

**Learning-to-rank objectives:**

| Paradigm | Input | Loss | Notes |
|---|---|---|---|
| **Pointwise** | Single doc + query | MSE / cross-entropy on relevance label | Simple; ignores relative ordering |
| **Pairwise** | (doc A, doc B) + query | Hinge/logistic on which is more relevant | More aligned with ranking objective |
| **Listwise** | Full ranked list | ListNet / LambdaRank | Best alignment; expensive to train |

**Metadata-based re-ranking:** hard filters (exact constraints: date range, author, department) applied before scoring; soft boosts (recency, source authority) blended into the final score.

## Query Strategies
{: #query-strategies}

### HyDE — Hypothetical Document Embeddings
{: #hyde}

([Gao et al. 2022](https://arxiv.org/abs/2212.10496))

Problem: the query "what causes Alzheimer's?" and a document chunk "β-amyloid plaques accumulate in Alzheimer's patients" have very different surface forms, causing semantic search to miss the match.

HyDE's solution: use the LLM to generate a *hypothetical* answer document for the query, then embed the hypothetical document (not the query) for retrieval.

```
Query → LLM → "Alzheimer's is caused by β-amyloid plaques…"
                    ↓ embed
              Hypothetical document vector → ANN search → Real documents
```

The hypothetical document lives in the same embedding space as real documents, closing the query-document distributional gap. Works particularly well for complex or abstract questions. Downside: adds one LLM inference per query.

### Query Expansion & Rewriting
{: #query-expansion}

**Multi-query generation.** Generate $N$ paraphrases of the query using the LLM; retrieve for each; merge and deduplicate candidates. Increases recall at the cost of $N$ retrieval passes.

**Step-back prompting.** For specific queries, generate a higher-level "step-back" question that abstracts away specifics before retrieving. Helps for questions that require broader background knowledge.

**Multi-turn query rewriting.** In conversational settings, reformulate the latest turn using conversation history to make it self-contained:

| Strategy | Mechanism | Notes |
|---|---|---|
| Latest turn only | Use the most recent message as query | Breaks on coreference ("tell me more about it") |
| Concatenated history | Append recent turns | Long queries; noise accumulates |
| Summarised history | Compress prior context to summary | Better signal-to-noise |
| Structured dialogue state | Extract intent + entities from history | Most robust; highest implementation cost |

**Sub-question decomposition.** For complex multi-part queries, decompose into atomic sub-questions, retrieve per sub-question, merge evidence before generation. Related to multi-hop RAG (see below).

### Multi-Hop RAG
{: #multi-hop}

Standard single-hop RAG retrieves once. Multi-hop RAG handles queries requiring sequential reasoning across multiple documents — each retrieval step is conditioned on what the previous step found.

```
"Who is the CEO of the company that acquired DeepMind?"
    ↓
Sub-question 1: "What company acquired DeepMind?" → retrieve → "Google"
    ↓
Sub-question 2: "Who is the CEO of Google?" → retrieve → "Sundar Pichai"
    ↓
Synthesis: "The CEO is Sundar Pichai"
```

Architecture:

- **Planner:** decomposes the original query into an ordered sequence of sub-questions
- **Retrieval controller:** selects documents for each sub-question, aware of what was retrieved previously
- **Synthesis:** generates the final answer from the accumulated evidence

Benchmarks: [MultiHop-RAG](https://arxiv.org/abs/2401.15391), HotpotQA, MuSiQue, 2WikiMultiHopQA.

## Advanced RAG Patterns
{: #advanced-patterns}

### ColBERT & Late Interaction
{: #colbert}

([Khattab & Zaharia 2020](https://arxiv.org/abs/2004.12832))

Standard dense retrieval compresses a document into a single vector — a severe information bottleneck. ColBERT retains token-level embeddings for both query and document, computing relevance via the **MaxSim operator**:

$$\text{ColBERT}(q, d) = \sum_{i \in q} \max_{j \in d} \vec{q}_i \cdot \vec{d}_j$$

Each query token finds its best-matching document token. This captures fine-grained alignment that single-vector representations lose. ColBERT v2 uses residual compression and denoised supervision to reduce storage cost.

**ColPali** (Faysse et al. 2024): extends ColBERT to multimodal documents. PDF pages are treated as images and embedded via a Vision Language Model (PaliGemma), enabling retrieval over visually complex documents (slides, figures, tables) without OCR.

**Late chunking** (JinaAI): a related idea — embed the full document through the encoder, then pool token representations into chunk embeddings. Each chunk embedding captures full-document context.

### Contextual Retrieval
{: #contextual-retrieval}

(Anthropic, 2024)

Before embedding each chunk, prepend a short LLM-generated context describing the chunk's role in the document:

```python
context = llm.generate(f"""
Document: {full_document}
Chunk: {chunk}
In 1-2 sentences, describe what context this chunk needs 
to be understood correctly within the document.
""")
indexed_chunk = context + "\n\n" + chunk
```

Combined with BM25, Anthropic reports a **49% reduction in failed retrievals**. The cost is one LLM call per chunk at ingestion time — acceptable for static corpora, expensive for rapidly changing ones.

### RAPTOR
{: #raptor}

([Sarthi et al. 2024](https://arxiv.org/abs/2401.18059)) Recursive Abstractive Processing for Tree-Organised Retrieval.

Standard RAG retrieves at a single granularity. RAPTOR builds a **retrieval tree**:

```
Level 0 (leaves): original chunks
Level 1: summaries of clusters of Level 0 chunks
Level 2: summaries of clusters of Level 1 summaries
…
Level N (root): document-level summary
```

Clustering uses Gaussian Mixture Models on chunk embeddings; summarisation uses an LLM. At query time, retrieval happens across all tree levels simultaneously — the system can retrieve both fine-grained detail chunks and coarse summaries depending on what matches the query.

Best for: long documents requiring both global context and specific detail (books, technical specs, research papers).

### GraphRAG
{: #graphrag}

([Edge et al. 2024, Microsoft](https://arxiv.org/abs/2404.16130))

Standard RAG treats documents as independent chunks. GraphRAG extracts a **knowledge graph** from the corpus and retrieves over the graph structure:

```
Documents → Entity extraction → Relation extraction → Knowledge Graph
                                                              ↓
Query → Entity linking → Graph traversal → Subgraph → LLM context
```

Key advantages:
- Multi-hop reasoning follows graph edges rather than requiring sequential retrieval calls
- Discovers cross-document connections not visible from individual chunks
- Summaries can be generated at community (cluster) level for global queries

**Local search:** retrieve the neighbourhood around query-relevant entities. Best for specific factual queries.

**Global search:** aggregate over community summaries. Best for thematic or analytical queries ("What are the main themes in this corpus?").

Cost: expensive ingestion (entity/relation extraction is LLM-intensive); complex graph maintenance. Worthwhile for dense, interconnected knowledge bases (legal documents, scientific literature).

### Hierarchical RAG
{: #hierarchical-rag}

Two-stage retrieval over documents indexed at multiple granularities:

1. Query high-level summaries to identify relevant documents or sections.
2. Retrieve fine-grained chunks from the identified documents only.

Reduces the search space for the precision stage. Effective for massive document collections where exhaustive dense search over all chunks is too slow.

### Corrective & Adaptive RAG
{: #corrective-rag}

**Corrective RAG (CRAG)** ([Yan et al. 2024](https://arxiv.org/abs/2401.15884)): adds a **retrieval evaluator** that scores retrieved documents as `{correct, ambiguous, incorrect}` before generation:

```
Query → Retrieval → Evaluator
    ├── Correct: proceed to generation
    ├── Ambiguous: supplement with web search
    └── Incorrect: discard, fall back to web search or knowledge-based generation
```

Prevents the generator from being misled by low-quality retrieved context.

**Adaptive RAG** ([Jeong et al. 2024](https://arxiv.org/abs/2403.14403)): learns to select retrieval strategy by query complexity. A lightweight classifier routes queries to:
- No retrieval (simple factual lookup within training knowledge)
- Single-step RAG (one retrieval pass)
- Multi-step RAG (iterative retrieval)

Reduces unnecessary retrieval overhead for simple queries while applying full multi-hop for complex ones.

**Self-RAG** ([Asai et al. 2023](https://arxiv.org/abs/2310.11511)): fine-tunes the LLM itself to output special reflection tokens (`[Retrieve]`, `[IsRel]`, `[IsSup]`, `[IsUse]`) that control whether retrieval is needed and whether the retrieved passage is relevant and supported. Tightly integrates retrieval decisions into the generation process.

### Agentic RAG
{: #agentic-rag}

Standard RAG is a fixed pipeline. Agentic RAG replaces the fixed pipeline with an LLM agent that makes autonomous decisions about *when* to retrieve, *what* to retrieve, *which source* to query, and *whether to iterate*. The RAG paradigm has evolved through five generations:

| Generation | Retrieval | Key addition |
|---|---|---|
| **Naïve RAG** | TF-IDF / BM25 | Static retrieve-read; no iteration |
| **Advanced RAG** | DPR, neural ranking | Multi-hop mechanisms, better ranking |
| **Modular RAG** | Hybrid sparse+dense | Composable pipelines, tool integration |
| **Graph RAG** | Graph-structured data | Multi-hop relational reasoning |
| **Agentic RAG** | Dynamic agent decisions | Autonomous planning, iterative refinement |

**Agent architecture.** An agentic RAG system wraps retrieval inside the standard agent loop:

```
Query → Agent (LLM)
    ├── Memory (short-term: context window; long-term: experience store)
    ├── Planning (task decomposition, reflection, self-critique)
    └── Tools: [vector_search, web_search, sql_query, api_call, …]
            ↓ observations
        Agent iterates until confident → final answer
```

**Agentic workflow patterns:**

| Pattern | Mechanism | Best for |
|---|---|---|
| **Prompt chaining** | Sequential subtasks, each conditioned on prior output | Linear workflows with dependencies |
| **Routing** | Classifier directs query to specialised retrieval path | Known query taxonomy |
| **Parallelisation** | Independent retrieval calls executed concurrently, results merged | Multi-source fan-out |
| **Orchestrator-workers** | Central agent delegates to specialised sub-agents | Complex multi-domain queries |
| **Evaluator-optimizer** | Evaluation agent scores output; optimizer agent refines | High-quality generation requirements |

**Single-agent router.** A single LLM classifies each query and routes it to the appropriate source — vector DB, SQL, web search, recommendations API. Simple, low-overhead, good for well-defined query taxonomies.

**Multi-agent RAG.** Specialised agents per source or domain. An orchestrator decomposes the query and routes sub-questions to specialists; each specialist retrieves from its assigned source; the orchestrator merges results. Strengths: modularity, scalability, task specialisation. Challenge: coordination overhead grows with agent count.

**Hierarchical agentic RAG.** Multi-tiered agent organisation: top-tier agents handle strategic planning and task delegation; lower-tier agents execute retrieval and synthesis. Enables strategic prioritisation across large, heterogeneous document collections. Challenge: inter-tier communication latency.

**Corrective RAG (CRAG)** — five-agent framework:

```
Query
  → [1] Context Retrieval Agent        (fetches initial candidates)
  → [2] Relevance Evaluation Agent     (flags irrelevant documents)
  → [3] Query Refinement Agent         (semantically optimises the query)
  → [4] External Knowledge Agent       (web search / alternative sources)
  → [5] Response Synthesis Agent       (generates final answer)
```

Each agent activates conditionally: if [2] finds all retrieved documents irrelevant, [3] rewrites the query and [4] fetches fresh evidence before [5] generates. Prevents the generator from being misled by low-quality context.

**Adaptive RAG** ([Jeong et al. 2024](https://arxiv.org/abs/2403.14403)): a lightweight classifier trained on automatically labelled data routes each query to one of three retrieval strategies:

- **No retrieval** — query answerable from model weights alone
- **Single-step RAG** — one retrieval pass sufficient
- **Multi-step RAG** — iterative retrieval required

Reduces unnecessary retrieval overhead for simple queries; reserves full multi-hop for complex ones.

**Agent-G (Graph RAG framework):** integrates graph knowledge bases with unstructured document retrieval. Three components: *Retriever Bank* (multiple heterogeneous retrievers), *Critic Module* (validates relevance and quality of retrieved data), *Dynamic Agent Interaction* (selects which retriever to invoke based on query). Captures multi-hop relationships invisible to chunk-based retrieval.

**GeAR (Graph-Enhanced Agent):** uses graph expansion to augment a base BM25 retriever — graph edges guide the agent to related nodes, enabling multi-hop retrieval without re-querying.

**Agentic Document Workflows (ADW).** End-to-end document automation pipelines: parsing → retrieval → reasoning → structured output with state maintenance across workflow steps. Integrates domain business rules. Applications: invoice processing, contract review, claims analysis.

**Active Retrieval (FLARE)** ([Jiang et al. 2023](https://arxiv.org/abs/2305.06983)): the LLM generates tentatively and triggers retrieval only when it detects low-confidence spans, interleaving retrieval into the generation stream rather than prepending all context upfront.

**Tool-calling RAG:**

```python
tools = [
    {"name": "vector_search", "description": "Search internal knowledge base"},
    {"name": "web_search",    "description": "Search the web for recent info"},
    {"name": "sql_query",     "description": "Query structured database"},
    {"name": "api_call",      "description": "Fetch live data from external API"},
]
```

The agent decides which tools to call, in what order, with what arguments — enabling fully adaptive multi-source retrieval without a fixed pipeline.

**When to use which architecture:**

| Architecture | Complexity | Query types | Main risk |
|---|---|---|---|
| Single-agent router | Low | Well-taxonomised, single-source | Fails on novel query types |
| Multi-agent | Medium | Multi-domain, parallel sources | Coordination overhead |
| Hierarchical | High | Large-scale, strategic prioritisation | Inter-tier latency |
| Corrective RAG | Medium | When retrieval quality is uncertain | 5-agent pipeline adds latency |
| Adaptive RAG | Low-Medium | Mixed simple/complex queries | Classifier errors misroute queries |

**Open challenges in agentic RAG:**
- Agent coordination and emergent behaviour control
- Evaluation beyond output quality — process-level evaluation (were retrieval decisions correct?)
- Memory management for long-horizon tasks
- Computational cost at scale (each agent hop adds latency)
- Safety and governance for autonomous retrieval decisions

## Generation & Context Assembly
{: #generation}

**Context window construction.** After retrieval and re-ranking, the top-K chunks must be assembled into the LLM's context window. Key decisions:

| Decision | Options | Tradeoff |
|---|---|---|
| **Ordering** | Most relevant first / last / interleaved | Lost-in-the-middle: central context overlooked; place most critical evidence first or last |
| **Deduplication** | Remove near-duplicate chunks | Saves context; risks losing complementary perspectives |
| **Citation anchoring** | Inline source references `[1]` | Required for attribution; adds tokens |
| **Context budget** | Max tokens per chunk × K | Must fit in context window with headroom for generation |

**Lost-in-the-middle** (Liu et al. 2023): LLMs are significantly better at using evidence placed at the beginning or end of the context window than in the middle. With 20 retrieved documents, accuracy on 10-document tasks drops ~15% when the answer is in positions 10–15. Mitigation: place the most relevant chunk first.

**Prompt structure for RAG:**

```
[System] You are a helpful assistant. Answer only from the provided context.
         If the context doesn't contain the answer, say so.

[Context]
[1] {chunk_1}
[2] {chunk_2}
…

[User] {query}

[Assistant] {response with inline citations [1][2]}
```

**Faithfulness enforcement.** Instruction fine-tuning on (context, question, grounded-answer) triples teaches the model to stay within retrieved evidence. RAG-specific instruction tuning (e.g., RAFT) additionally trains models to identify which retrieved documents are distractors.

## Evaluation
{: #evaluation}

### RAGAS Metrics
{: #ragas}

[RAGAS](https://arxiv.org/abs/2309.15217) (Es et al. 2023) provides four reference-free metrics for end-to-end RAG evaluation using an LLM judge:

$$F_\text{RAGAS} = \frac{1}{4}\left(F_\text{faithfulness} + P_\text{context} + R_\text{context} + R_\text{answer}\right)$$

| Metric | Formula | What it measures |
|---|---|---|
| **Faithfulness** | $\frac{\text{supported claims}}{\text{total claims in answer}}$ | Does the answer stay within retrieved context? |
| **Context Precision** | $\frac{\text{relevant docs used}}{\text{total docs used}}$ | Is retrieved context relevant? |
| **Context Recall** | $\frac{\text{relevant docs used}}{\text{relevant docs available}}$ | Does retrieval cover all necessary evidence? |
| **Answer Relevance** | $\cos(\text{embed}(q),\, \text{embed}(a))$ | Does the answer address the query? |

**Faithfulness** is the most critical production metric — an unfaithful answer means the generator hallucinated beyond retrieved evidence.

**Context Precision vs. Recall tradeoff:** increasing K (retrieved documents) improves recall but degrades precision (more irrelevant context). Tune K on the validation set using RAGAS Context Precision as the signal.

### Retrieval Metrics
{: #retrieval-metrics}

| Metric | Formula | Notes |
|---|---|---|
| **Precision@K** | $\frac{\text{relevant in top-}K}{K}$ | Quality of the retrieved set |
| **Recall@K** | $\frac{\text{relevant in top-}K}{\text{total relevant}}$ | Coverage of the retrieved set |
| **MRR** | $\frac{1}{|Q|}\sum_q \frac{1}{\text{rank}(q)}$ | Rewards high rank for the first relevant doc |
| **NDCG@K** | $\sum_i \frac{2^{r_i}-1}{\log_2(i+1)}$ normalised | Graded relevance, position-weighted |
| **Hit Rate@K** | $\mathbb{1}[\text{relevant doc in top-}K]$ | Does the right document appear at all? |

NDCG@K is the standard for re-ranker evaluation; Hit Rate@K (often called Recall@1) is the most interpretable for end users.

### Generation Metrics
{: #generation-metrics}

| Metric | Type | Notes |
|---|---|---|
| **Faithfulness (RAGAS)** | LLM-judge | Primary: does generation stay grounded? |
| **BERTScore** | Reference-based | Contextual embedding similarity to ground truth |
| **ROUGE-L** | Reference-based | LCS recall; useful for summarisation |
| **Exact match** | Reference-based | For factoid Q&A with known ground truth |
| **String presence** | Heuristic | Is the expected entity/phrase present? |
| **LLM-as-judge (G-Eval)** | LLM-judge | Rates coherence, relevance, factual consistency |

### Benchmarks
{: #benchmarks}

| Benchmark | Focus | Notes |
|---|---|---|
| **[BEIR](https://arxiv.org/abs/2104.08663)** | Retrieval generalisation | 18 diverse retrieval tasks; zero-shot evaluation |
| **[MS MARCO](https://arxiv.org/abs/1611.09268)** | Web passage retrieval | 8.8M passages; standard re-ranker training set |

## Production System Design
{: #production}

### Reference Architecture
{: #architecture}

```
                    ┌──────────────────────────────┐
                    │        Ingestion Pipeline     │
  Raw documents ───→│  Parse → Chunk → Embed → Index│───→ Vector DB
                    └──────────────────────────────┘

  ┌─────────────┐   ┌──────────────────────────────────────────────────┐
  │   User      │   │                Query Pipeline                    │
  │   Query  ───│──→│  Rewrite → BM25 + Dense → RRF → Re-rank → Trim  │
  └─────────────┘   └──────────────────────┬───────────────────────────┘
                                           │ Top-K chunks
                                    ┌──────▼──────┐
                                    │ LLM + prompt │
                                    └──────┬───────┘
                                           │ Response + citations
                                    ┌──────▼──────┐
                                    │  Post-proc  │ (citation verification, safety)
                                    └─────────────┘
```

**Ingestion design decisions:**

| Decision | Recommendation | Rationale |
|---|---|---|
| Chunk size | 256–512 tokens for Q&A | Balance between precision and context completeness |
| Overlap | 10–15% | Prevent boundary loss |
| Embedding model | BGE-large or text-embedding-3-large | MTEB-validated quality |
| Index type | HNSW (Qdrant, Weaviate) | Best recall-latency for <100M vectors |
| Metadata | source, date, section, access level | Enables filtering and attribution |

**Query pipeline deployment recipes:**

| Use case | Architecture | Notes |
|---|---|---|
| Internal knowledge base | BM25 + dense, cross-encoder re-rank, K=10 | Balance recall and precision |
| Customer-facing chatbot | Contextual retrieval + hybrid, K=5, citations required | Faithfulness-critical |
| Research assistant | Multi-hop + RAPTOR + web fallback | Broad, complex queries |
| Code search | BM25-dominant (identifiers matter), K=20 | Exact keyword critical |

### Latency & Cost
{: #latency}

End-to-end RAG latency budget breakdown:

| Stage | Typical latency | Optimisation levers |
|---|---|---|
| Query embedding | 5–20ms | Small embedding model; GPU |
| BM25 retrieval | 1–5ms | Pre-built inverted index |
| ANN search | 5–30ms | HNSW vs. IVF; in-memory index |
| Cross-encoder re-rank (K=100) | 50–200ms | Smaller model; reduce K; cache |
| LLM generation | 500–5000ms | Dominates; streaming for UX |

**Cost levers:**

- Reduce K at retrieval (fewer embeddings computed)
- Use bi-encoder instead of cross-encoder for re-ranking
- Cache retrieval results for repeated/similar queries (embedding similarity cache)
- Reduce LLM context length by tighter chunk trimming
- Use a smaller LLM for generation; reserve large model for high-stakes queries

**K selection tradeoff:**

```
Precision@K vs. K: decreases as K grows (more irrelevant docs)
Recall@K vs. K:    increases as K grows (more coverage)
LLM cost vs. K:    linear in context tokens
```

Typical production: K=100 to re-ranker → K=5–20 to LLM.

### Failure Modes
{: #failure-modes}

Seven common RAG failure points:

| # | Failure | Symptom | Fix |
|---|---|---|---|
| 1 | **Missing retrieval** | Relevant document never retrieved | Lower similarity threshold; increase K; add BM25; check chunking |
| 2 | **Irrelevant retrieval** | Retrieved chunks are off-topic | Tighten re-ranker threshold; improve embedding model; metadata filter |
| 3 | **Incomplete context** | Answer requires multiple chunks; only one retrieved | Increase K; add sentence-window or auto-merge chunking |
| 4 | **Context length overflow** | Top-K chunks exceed LLM context | Reduce chunk size; reduce K; use chunk summarisation |
| 5 | **Lost-in-the-middle** | Correct chunk retrieved but ignored by LLM | Place most relevant chunk first or last; reduce total chunks |
| 6 | **Hallucination in generation** | LLM adds facts not in retrieved context | Add faithfulness instruction; RAFT fine-tuning; RAGAS monitoring |
| 7 | **Safety constraint violation** | Response violates policy despite clean retrieval | Post-generation safety classifier; output guardrails |

Additional failure modes:

| Failure | Root cause | Fix |
|---|---|---|
| **Chunking boundary split** | Relevant evidence split across chunks | Increase overlap; sentence-window retrieval |
| **Semantic over-generalisation** | Retriever returns topically related but factually wrong chunks | Hard metadata filter before embedding search |
| **Stale index** | Document updated but index not refreshed | Incremental indexing pipeline; TTL-based invalidation |
| **Retrieval latency spike** | ANN index not warmed; cold start | Pre-warm index; keep hot in memory |
| **Embedding distribution shift** | Embedding model updated; old and new embeddings incomparable | Re-index all documents when model changes; version the index |

### Monitoring
{: #monitoring}

**Per-query metrics to log:**

```json
{
  "query_id": "...",
  "query": "...",
  "retrieved_chunks": [...],
  "reranker_scores": [...],
  "faithfulness_score": 0.91,
  "context_precision": 0.78,
  "answer_relevance": 0.85,
  "retrieval_latency_ms": 45,
  "generation_latency_ms": 1200,
  "total_context_tokens": 3200
}
```

**Dashboards to build:**

| Signal | Alert threshold | Action |
|---|---|---|
| Faithfulness score < 0.8 | P50 over 1h | Investigate hallucination; check context quality |
| Context precision < 0.5 | P50 over 1h | Retrieval quality degraded; check embedding model |
| Hit Rate@5 < 0.7 | Offline eval | Chunking or retrieval regression |
| Retrieval latency P99 > 500ms | Any | ANN index issue; scale query layer |
| Unanswered rate > 10% | Over 1h | Coverage gap; expand corpus or lower threshold |

**Offline evaluation cadence:** run RAGAS + BEIR subset weekly on the retrieval pipeline; run end-to-end LLM-judge evaluation monthly or on any corpus or model change.

> **Interview question:** Your RAG system's faithfulness score has dropped from 0.92 to 0.74 over the past week. How do you diagnose and fix it?
>
> *Start by decomposing: is the problem in retrieval or generation? Check context precision — if that also dropped, the retriever is returning worse context and the generator is hallucinating to fill gaps. If context precision is stable, the generator changed (model update? prompt change?). For a retrieval root cause: check if the corpus was updated — new documents may have different structure that breaks chunking boundaries, or the embedding distribution shifted if the embedding model was updated without re-indexing. Inspect retrieved chunks for a sample of low-faithfulness queries: are they actually relevant? If they're relevant but faithfulness is still low, the generator is ignoring context — check the system prompt for faithfulness instruction, and consider whether the LLM context is too long (lost-in-the-middle). Fix hierarchy: prompt fix first (cheapest), then chunking fix, then re-indexing, then fine-tuning (most expensive).*
