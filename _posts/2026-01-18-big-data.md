## Why Big Data Frameworks Exist {#why-big-data}

A single machine can sort 1 TB of data in a few hours. When your data is 1 PB, you need 1,000 machines working together. The problems that arise at that scale:

- **Distributed storage**: data must be split across many disks; reads/writes must be coordinated
- **Fault tolerance**: any of 1,000 machines will fail; jobs must survive without restarting from scratch
- **Data locality**: moving 100 TB across a network is slow; compute should run where data already lives
- **Coordination**: dividing work, tracking progress, collecting results across machines

```
Single machine:
  Data: 1 TB on one disk
  CPU: process sequentially
  Failure: job dies, restart from scratch

Distributed:
  Data: 1 TB split across 100 nodes × 10 GB each (+ 3× replication = 300 GB/node)
  CPU: 100 nodes process their local data simultaneously
  Failure: one node dies → use replica on another node, recompute only failed partition
  
Throughput scales linearly with nodes (mostly).
Coordination overhead grows sub-linearly.
```

The key insight: **move the computation to the data**, not the data to the computation.

## Hadoop Ecosystem {#hadoop}

Hadoop (2006) pioneered distributed data processing. Modern stacks have largely replaced its components, but understanding them explains why Spark was built.

### HDFS {#hdfs}

**Hadoop Distributed File System**: splits large files into 128 MB blocks, replicates each block 3× across different nodes/racks.

```
File: 400 MB → Block A (128MB), Block B (128MB), Block C (144MB)

Block A → Node 1 (primary), Node 3 (replica), Node 7 (replica)
Block B → Node 2 (primary), Node 5 (replica), Node 9 (replica)
Block C → Node 4 (primary), Node 1 (replica), Node 6 (replica)

NameNode: stores metadata (which blocks belong to which file, where each block lives)
DataNodes: store the actual block data

If Node 2 dies: Block B still accessible from Node 5 or Node 9.
NameNode notices replication factor is now 2, instructs another node to re-replicate.
```

**NameNode is a single point of failure** in classic Hadoop. Modern deployments use High Availability NameNode (active-standby pair with ZooKeeper coordination).

### MapReduce {#mapreduce}

The original programming model for distributed computation. Every job has two phases:

```python
# Word count — the "hello world" of big data

# MAP phase: runs in parallel on each data partition
def map(document):
    for word in document.split():
        emit(word, 1)
# Output from all mappers: [("the", 1), ("cat", 1), ("the", 1), ("sat", 1), ...]

# SHUFFLE: framework sorts and groups by key, sends to reducers
# [("cat", [1]), ("sat", [1]), ("the", [1, 1]), ...]

# REDUCE phase: runs in parallel on each key group
def reduce(key, values):
    emit(key, sum(values))
# Output: [("cat", 1), ("sat", 1), ("the", 2)]
```

**Why MapReduce is slow**: every stage writes results to HDFS. A multi-step pipeline writes to disk between every step. 10-stage pipeline = 10 reads + 10 writes to HDFS. Disk I/O dominates.

Spark fixed this by keeping data **in memory** across stages.

### YARN {#yarn}

Yet Another Resource Negotiator — the cluster resource manager. Allocates CPU and memory to applications (Spark, Flink, etc.) running on the cluster. Spark on YARN is still common in enterprise environments.

```
YARN ResourceManager: allocates cluster resources
YARN NodeManagers: run on each node, manage local resources
ApplicationMaster: one per Spark job, negotiates resources from RM, manages executors
```

### Hive & HiveQL {#hive}

SQL interface over HDFS/MapReduce. Write SQL, Hive translates to MapReduce jobs. Slow (minutes per query), but enabled analysts to query big data without writing Java.

Modern replacement: **Spark SQL** (10–100× faster), **Presto/Trino** (sub-minute interactive queries).

## Apache Spark {#spark}

Spark (2014) replaced MapReduce for most workloads by keeping intermediate data in memory. A Spark job can be 10–100× faster than the equivalent MapReduce job.

### Internals: DAG, Stages, Shuffles {#spark-internals}

```
Your Spark code defines a computation graph (DAG):

df.filter(col > 5)          # narrow transformation
  .groupBy("category")      # wide transformation (needs shuffle)
  .agg(sum("value"))        # aggregation
  .orderBy("sum")           # wide (sort requires all data)

Spark builds a DAG then optimises and executes it:

Stage 1 (no shuffle):                  Stage 2:
  Partition 1: read → filter           Partition A: partial agg → sort
  Partition 2: read → filter    ──→    Partition B: partial agg → sort
  Partition 3: read → filter           Partition C: partial agg → sort
      (all in memory)           SHUFFLE
                                (expensive: serialise, write to disk,
                                 transfer across network, deserialise)
```

**Narrow vs Wide transformations:**

| Narrow | Wide (requires shuffle) |
|---|---|
| `filter`, `map`, `flatMap` | `groupBy`, `join`, `distinct` |
| `select`, `withColumn` | `orderBy`, `repartition` |
| `union` (same partitioning) | `reduceByKey`, `aggregateByKey` |
| Data stays on same partition | Data moves across partitions (network) |

**Shuffle** is the most expensive operation in Spark. Each shuffle:
1. Writes shuffle data to local disk (spill)
2. Transfers data across the network
3. Reads from disk on receiving side

Minimise shuffles. When you must shuffle, control partition count.

**Catalyst Optimizer**: Spark SQL's query planner. Applies rule-based and cost-based optimisations — column pruning, predicate pushdown, join reordering, constant folding. Works automatically on DataFrames. Does not work on raw RDDs.

**Tungsten**: Spark's off-heap memory management and code generation. Generates JVM bytecode at runtime, bypasses JVM garbage collection overhead, uses cache-friendly memory layouts.

### RDDs {#rdd}

**Resilient Distributed Dataset** — Spark's foundational abstraction. An immutable, partitioned collection of records.

```python
from pyspark import SparkContext

sc = SparkContext("local[4]", "MyApp")  # 4 local threads

# Create RDD from data
rdd = sc.parallelize([1, 2, 3, 4, 5, 6, 7, 8], numSlices=4)

# Transformations (lazy — nothing runs yet)
filtered = rdd.filter(lambda x: x % 2 == 0)   # [2, 4, 6, 8]
doubled  = filtered.map(lambda x: x * 2)       # [4, 8, 12, 16]

# Actions (trigger execution)
result = doubled.collect()   # [4, 8, 12, 16] — pulls to driver
total  = doubled.reduce(lambda a, b: a + b)    # 40
count  = doubled.count()     # 4

# Key-value RDD operations
pairs = sc.parallelize([("a", 1), ("b", 2), ("a", 3), ("b", 4)])
grouped = pairs.groupByKey().mapValues(list).collect()
# [("a", [1, 3]), ("b", [2, 4])]

reduced = pairs.reduceByKey(lambda a, b: a + b).collect()
# [("a", 4), ("b", 6)]   — prefer over groupByKey (less memory)

# Word count with RDDs
text_rdd = sc.textFile("s3://bucket/logs/*.txt")
words = text_rdd.flatMap(lambda line: line.split())
word_counts = words.map(lambda w: (w, 1)).reduceByKey(lambda a, b: a + b)
word_counts.saveAsTextFile("s3://bucket/output/word_counts")
```

> **Use DataFrames over RDDs.** RDDs bypass the Catalyst optimizer and Tungsten — you lose all automatic optimisation. RDDs are useful only when you need fine-grained control over partitioning or are working with non-tabular data (e.g., raw bytes, custom objects).

### DataFrames & Datasets {#dataframe}

DataFrames are Spark's high-level API — distributed tables with named columns and schema. Use these for almost everything.

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DoubleType
from pyspark.sql.window import Window

spark = SparkSession.builder \
    .appName("MyApp") \
    .config("spark.sql.shuffle.partitions", "200") \
    .config("spark.executor.memory", "4g") \
    .config("spark.executor.cores", "4") \
    .getOrCreate()

# ── Reading data ────────────────────────────────────────────────────────
# Parquet (preferred — columnar, compressed, schema-aware)
df = spark.read.parquet("s3://bucket/data/events/")

# CSV with schema inference (slow for large files — provide schema)
schema = StructType([
    StructField("user_id",   StringType(),  nullable=False),
    StructField("event",     StringType(),  nullable=True),
    StructField("timestamp", StringType(),  nullable=True),
    StructField("value",     DoubleType(),  nullable=True),
])
df = spark.read.csv("s3://bucket/events.csv", header=True, schema=schema)

# JSON
df = spark.read.json("s3://bucket/logs/*.json")

# Delta Lake (with transactions)
df = spark.read.format("delta").load("s3://bucket/delta/events")

# ── Basic operations ────────────────────────────────────────────────────
df.printSchema()
df.show(5, truncate=False)
df.describe().show()   # count, mean, stddev, min, max per column

# Select, filter, rename
result = (df
    .select("user_id", "event", "value", F.to_timestamp("timestamp").alias("ts"))
    .filter(F.col("value") > 0)
    .filter(F.col("event").isin(["click", "purchase", "view"]))
    .withColumn("value_usd", F.col("value") / 100)
    .drop("value")
)

# ── Aggregations ────────────────────────────────────────────────────────
agg = (df
    .groupBy("user_id", "event")
    .agg(
        F.count("*").alias("event_count"),
        F.sum("value").alias("total_value"),
        F.avg("value").alias("avg_value"),
        F.max("timestamp").alias("last_seen"),
        F.countDistinct("session_id").alias("unique_sessions"),
        F.collect_list("value").alias("all_values"),  # careful: can OOM
    )
)

# ── Window functions ────────────────────────────────────────────────────
window_spec = Window.partitionBy("user_id").orderBy("timestamp")

df_with_rank = df.withColumn("event_rank", F.rank().over(window_spec))
df_with_lag  = df.withColumn("prev_value", F.lag("value", 1).over(window_spec))
df_with_cum  = df.withColumn("cumulative_value", F.sum("value").over(window_spec))

# Rolling window: last 7 days
days_7 = Window.partitionBy("user_id") \
               .orderBy(F.unix_timestamp("timestamp")) \
               .rangeBetween(-7 * 86400, 0)
df_rolling = df.withColumn("rolling_7d_value", F.sum("value").over(days_7))

# ── UDFs (use sparingly — bypasses Tungsten) ────────────────────────────
from pyspark.sql.types import StringType

@F.udf(returnType=StringType())
def categorise_value(value):
    if value is None: return "unknown"
    if value < 10:    return "low"
    if value < 100:   return "medium"
    return "high"

# Better: use pandas UDF (vectorised, much faster)
from pyspark.sql.functions import pandas_udf
import pandas as pd

@pandas_udf(StringType())
def categorise_value_fast(series: pd.Series) -> pd.Series:
    return series.apply(lambda v: "low" if v < 10 else "medium" if v < 100 else "high")

df = df.withColumn("category", categorise_value_fast("value"))

# ── Writing data ────────────────────────────────────────────────────────
(result
    .repartition(100)    # control output file count
    .write
    .mode("overwrite")   # overwrite | append | ignore | errorifexists
    .partitionBy("date", "event")   # partition on disk for fast filtering
    .parquet("s3://bucket/output/processed/")
)
```

### Joins & Shuffle Optimisation {#spark-joins}

Joins are the most common source of performance problems in Spark.

```python
large_df  = spark.read.parquet("s3://bucket/events/")      # 500 GB
medium_df = spark.read.parquet("s3://bucket/sessions/")    # 50 GB
small_df  = spark.read.parquet("s3://bucket/categories/")  # 10 MB

# ── Sort-Merge Join (default for large tables) ──────────────────────────
# Both sides shuffled and sorted by join key, then merged
# Good: any size, distributed
# Bad: two shuffles (one per table)
result = large_df.join(medium_df, on="session_id", how="inner")

# ── Broadcast Join (best when one side is small) ────────────────────────
# Small table broadcasted to all executors — zero shuffle on large side
from pyspark.sql.functions import broadcast

result = large_df.join(broadcast(small_df), on="category_id", how="left")
# Spark auto-broadcasts tables < spark.sql.autoBroadcastJoinThreshold (default 10 MB)
# Increase threshold:
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 100 * 1024 * 1024)  # 100 MB

# ── Bucket Join (pre-partitioned tables, zero shuffle) ──────────────────
# Requires tables to be written as bucketed
large_df.write \
    .bucketBy(200, "user_id") \
    .sortBy("user_id") \
    .saveAsTable("events_bucketed")

small_df.write \
    .bucketBy(200, "user_id") \
    .sortBy("user_id") \
    .saveAsTable("profiles_bucketed")

# Join with no shuffle (both sides already partitioned the same way)
spark.sql("SELECT * FROM events_bucketed e JOIN profiles_bucketed p ON e.user_id = p.user_id")

# ── Skew join — when one key has vastly more data than others ──────────
# e.g., user_id = "anonymous" has 80% of all rows

# Method 1: salt the skewed key
import random
N_SALTS = 10

skewed_df = large_df.withColumn(
    "salted_key",
    F.concat(F.col("user_id"), F.lit("_"), (F.rand() * N_SALTS).cast("int").cast("string"))
)
small_replicated = small_df.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N_SALTS)]))) \
    .withColumn("salted_key", F.concat(F.col("user_id"), F.lit("_"), F.col("salt").cast("string")))

result = skewed_df.join(small_replicated, on="salted_key")

# Method 2: Spark 3.x Adaptive Query Execution (AQE) handles this automatically
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
```

### Tuning: Partitioning, Caching, Memory {#spark-tuning}

```python
# ── Partitioning ─────────────────────────────────────────────────────────
# Check current partition count
print(df.rdd.getNumPartitions())   # e.g., 2000

# Too many partitions: overhead per task > useful work (aim for 100-500MB/partition)
df_coalesced = df.coalesce(200)    # reduce without shuffle

# Too few partitions: not enough parallelism, tasks too large
df_repartitioned = df.repartition(500)             # shuffle
df_repartitioned = df.repartition(500, "user_id")  # shuffle, partition by column

# Golden rule: target 128-512 MB per partition
# num_partitions = total_data_size_bytes / target_partition_size_bytes

# Shuffle partitions (set before joins/aggregations)
spark.conf.set("spark.sql.shuffle.partitions", "400")   # default 200, often wrong

# AQE auto-tuning (Spark 3+) — adjusts shuffle partitions at runtime
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

# ── Caching ─────────────────────────────────────────────────────────────
from pyspark import StorageLevel

# Cache in memory (default)
df.cache()                          # MEMORY_AND_DISK
df.persist(StorageLevel.MEMORY_AND_DISK_SER)   # serialised (less memory, slower)
df.persist(StorageLevel.DISK_ONLY)             # when memory is tight

# Check if cached
spark.catalog.isCached("my_table")

# Always unpersist when done
df.unpersist()

# When to cache:
# ✓ DataFrame used multiple times in the same job
# ✓ Expensive to recompute (many transformations, complex joins)
# ✗ Used only once — wastes memory
# ✗ Larger than available memory — thrashing

# ── Memory configuration ─────────────────────────────────────────────────
# spark.executor.memory: total JVM heap per executor
# spark.executor.memoryOverhead: off-heap memory (10% or 384MB, whichever larger)
# spark.memory.fraction: fraction of heap for execution + storage (default 0.6)
# spark.memory.storageFraction: of the above, reserved for cache (default 0.5)

# Executor sizing rule of thumb:
#   - 4-5 cores per executor (more → GC pressure; fewer → overhead)
#   - 4 GB RAM per core
#   - Leave 1 core + ~1 GB per node for OS/YARN daemons
# e.g., node with 32 cores, 128 GB RAM:
#   6 executors × 5 cores × 21 GB RAM (128/6 ≈ 21, minus OS overhead)

# ── Explain plan ─────────────────────────────────────────────────────────
df.explain(mode="formatted")   # shows physical plan, join types, filters pushed down
# Look for:
#   BroadcastHashJoin → good (small table broadcast)
#   SortMergeJoin     → check if broadcast possible
#   Exchange          → shuffle (each Exchange = one shuffle)
#   FileScan with pushed filters → predicate pushdown working
```

### Structured Streaming {#spark-streaming}

Spark Structured Streaming treats a stream as an unbounded DataFrame — same API, continuous execution.

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

spark = SparkSession.builder.appName("StreamingApp").getOrCreate()

# ── Read from Kafka ──────────────────────────────────────────────────────
raw_stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "kafka:9092") \
    .option("subscribe", "events") \
    .option("startingOffsets", "latest") \
    .load()

# Kafka gives: key, value (bytes), topic, partition, offset, timestamp
schema = StructType([
    StructField("user_id", StringType()),
    StructField("event",   StringType()),
    StructField("value",   DoubleType()),
    StructField("ts",      TimestampType()),
])

events = raw_stream.select(
    F.from_json(F.col("value").cast("string"), schema).alias("data"),
    F.col("timestamp").alias("kafka_ts")
).select("data.*", "kafka_ts")

# ── Windowed aggregation ─────────────────────────────────────────────────
windowed = (events
    .withWatermark("ts", "10 minutes")    # tolerate up to 10 min late data
    .groupBy(
        F.window("ts", "5 minutes"),      # tumbling 5-minute windows
        "event"
    )
    .agg(
        F.count("*").alias("event_count"),
        F.sum("value").alias("total_value"),
    )
)

# ── Output sinks ─────────────────────────────────────────────────────────
# Console (dev only)
query = windowed.writeStream \
    .format("console") \
    .outputMode("update") \
    .start()

# Parquet files (micro-batch)
query = windowed.writeStream \
    .format("parquet") \
    .option("path", "s3://bucket/streaming_output/") \
    .option("checkpointLocation", "s3://bucket/checkpoints/streaming/") \
    .outputMode("append") \
    .trigger(processingTime="1 minute") \  # micro-batch every 1 min
    .start()

# Kafka sink (stream-to-stream)
query = events.select(
    F.col("user_id").alias("key"),
    F.to_json(F.struct("*")).alias("value")
).writeStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "kafka:9092") \
    .option("topic", "processed_events") \
    .option("checkpointLocation", "s3://bucket/checkpoints/kafka-sink/") \
    .start()

# Delta Lake sink (ACID, time travel)
query = windowed.writeStream \
    .format("delta") \
    .option("checkpointLocation", "s3://bucket/checkpoints/delta/") \
    .outputMode("append") \
    .start("s3://bucket/delta/windowed_events/")

query.awaitTermination()

# Output modes:
#   append:  only new rows (use for aggregations with watermark)
#   update:  only changed rows since last trigger
#   complete: full result table every trigger (use for small aggregations)
```

### MLlib & Spark ML {#spark-ml}

```python
from pyspark.ml import Pipeline
from pyspark.ml.feature import (
    VectorAssembler, StringIndexer, StandardScaler,
    OneHotEncoder, PCA
)
from pyspark.ml.classification import RandomForestClassifier, GBTClassifier
from pyspark.ml.evaluation import BinaryClassificationEvaluator
from pyspark.ml.tuning import CrossValidator, ParamGridBuilder

# ── Feature engineering pipeline ─────────────────────────────────────────
# Index categorical column
indexer = StringIndexer(inputCol="category", outputCol="category_idx", handleInvalid="keep")

# One-hot encode
encoder = OneHotEncoder(inputCol="category_idx", outputCol="category_vec")

# Assemble features
assembler = VectorAssembler(
    inputCols=["category_vec", "value", "count", "days_since_last"],
    outputCol="features_raw"
)

# Scale
scaler = StandardScaler(inputCol="features_raw", outputCol="features", withStd=True, withMean=True)

# Model
rf = RandomForestClassifier(
    featuresCol="features",
    labelCol="label",
    numTrees=100,
    maxDepth=10,
    seed=42,
)

# Pipeline chains all steps
pipeline = Pipeline(stages=[indexer, encoder, assembler, scaler, rf])

# Train/test split
train, test = df.randomSplit([0.8, 0.2], seed=42)
model = pipeline.fit(train)

# Evaluate
predictions = model.transform(test)
evaluator = BinaryClassificationEvaluator(labelCol="label", metricName="areaUnderROC")
print("AUC:", evaluator.evaluate(predictions))

# Hyperparameter tuning
param_grid = (ParamGridBuilder()
    .addGrid(rf.numTrees, [50, 100, 200])
    .addGrid(rf.maxDepth, [5, 10, 15])
    .build()
)

cv = CrossValidator(
    estimator=pipeline,
    estimatorParamMaps=param_grid,
    evaluator=evaluator,
    numFolds=3,
    parallelism=4,   # evaluate 4 param combos in parallel
)
cv_model = cv.fit(train)
print("Best AUC:", evaluator.evaluate(cv_model.transform(test)))

# Save and load
model.save("s3://bucket/models/rf_pipeline")
from pyspark.ml import PipelineModel
loaded = PipelineModel.load("s3://bucket/models/rf_pipeline")
```

### Spark Pitfalls {#spark-pitfalls}

| Pitfall | Symptom | Fix |
|---|---|---|
| **Too many small files** | Thousands of 1 MB parquet files → slow reads | `coalesce(N)` before write; use Delta Lake with `OPTIMIZE` |
| **Default shuffle partitions (200)** | Huge partitions OOM or tiny partitions waste overhead | Set `spark.sql.shuffle.partitions` based on data size; use AQE |
| **`collect()` on large DataFrame** | Driver OOM | Only collect aggregated/small results; use `write` instead |
| **UDFs instead of built-ins** | 10× slower; bypasses Tungsten | Use `pyspark.sql.functions` built-ins; if must UDF, use pandas_udf |
| **`groupByKey` in RDD API** | All values for a key shuffled to one node → OOM | Use `reduceByKey` or `aggregateByKey` (pre-aggregate locally) |
| **No watermark on streaming aggregations** | State grows forever → OOM | Always add `.withWatermark()` for streaming window aggregations |
| **Cartesian join** | N×M rows, exponential explosion | Ensure join condition exists; check for accidental `crossJoin` |
| **Reading whole partition when only one column needed** | Slow; wastes I/O | Store as Parquet (columnar); Spark reads only needed columns |
| **Not partitioning output on read-time filter columns** | Full scan on every query | `write.partitionBy("date", "region")` for columns commonly filtered |
| **Cache without unpersist** | Cache fills up, evicts hot data | `df.unpersist()` after you're done with a cached DataFrame |

## Apache Kafka {#kafka}

Kafka is a distributed event streaming platform. It's the glue between producers (services that generate events) and consumers (services that process them).

### Internals: Topics, Partitions, Offsets {#kafka-internals}

```
Topic: "user-events"
  Partition 0: [msg@0] [msg@1] [msg@2] [msg@3] ...
  Partition 1: [msg@0] [msg@1] [msg@2] ...
  Partition 2: [msg@0] [msg@1] ...

Each message has:
  - Offset: sequential ID within a partition (immutable)
  - Key: used to determine partition (same key → same partition → ordered)
  - Value: the payload (bytes)
  - Timestamp: event time or ingestion time
  - Headers: metadata key-value pairs

Consumers track their position using (topic, partition, offset).
Committed offsets are stored in __consumer_offsets topic.
```

**Retention**: Kafka keeps messages for a configurable duration (default 7 days) regardless of whether they've been consumed. Multiple consumer groups can read the same topic independently.

**Replication**: each partition has one **leader** and N-1 **followers** (replicas). Producers/consumers talk to the leader. Followers replicate. If the leader dies, a follower is elected leader. `replication.factor=3` is standard for production.

**ISR (In-Sync Replicas)**: the set of replicas that are caught up with the leader. `min.insync.replicas=2` means a write is only acknowledged when at least 2 replicas have it — protects against data loss.

### Producers & Consumers {#kafka-producers}

```python
from confluent_kafka import Producer, Consumer, KafkaError
import json
from datetime import datetime

# ── Producer ─────────────────────────────────────────────────────────────
producer = Producer({
    "bootstrap.servers": "kafka1:9092,kafka2:9092,kafka3:9092",
    "acks": "all",              # wait for all ISR replicas to acknowledge
    "retries": 5,
    "retry.backoff.ms": 100,
    "linger.ms": 5,             # batch messages for 5ms before sending
    "batch.size": 65536,        # 64KB batch size
    "compression.type": "snappy",  # compress batches
    "enable.idempotence": True, # exactly-once producer semantics
})

def delivery_callback(err, msg):
    if err:
        print(f"Delivery failed: {err}")
    else:
        print(f"Delivered to {msg.topic()}[{msg.partition()}] @ offset {msg.offset()}")

# Send a message
event = {
    "user_id": "u123",
    "event": "purchase",
    "value": 99.99,
    "timestamp": datetime.utcnow().isoformat(),
}

producer.produce(
    topic="user-events",
    key="u123",             # same user → same partition → ordered per user
    value=json.dumps(event).encode(),
    callback=delivery_callback,
)

producer.flush()   # wait for all outstanding messages to be delivered

# ── Consumer ─────────────────────────────────────────────────────────────
consumer = Consumer({
    "bootstrap.servers": "kafka1:9092,kafka2:9092,kafka3:9092",
    "group.id": "analytics-service",   # consumer group
    "auto.offset.reset": "earliest",   # start from beginning if no committed offset
    "enable.auto.commit": False,        # manual commit for at-least-once
    "max.poll.interval.ms": 300000,    # 5 min; increase for slow processing
    "session.timeout.ms": 30000,
})

consumer.subscribe(["user-events"])

try:
    while True:
        msg = consumer.poll(timeout=1.0)
        if msg is None:
            continue
        if msg.error():
            if msg.error().code() == KafkaError._PARTITION_EOF:
                continue
            raise KafkaError(msg.error())
        
        event = json.loads(msg.value().decode())
        
        try:
            process_event(event)
            # Only commit after successful processing (at-least-once)
            consumer.commit(message=msg)
        except Exception as e:
            print(f"Processing failed: {e}")
            # Don't commit — message will be redelivered
            # Send to dead letter queue for investigation
            send_to_dlq(msg, str(e))

finally:
    consumer.close()

# ── Batch consumer (higher throughput) ────────────────────────────────────
msgs = consumer.consume(num_messages=1000, timeout=1.0)
events = [json.loads(m.value()) for m in msgs if not m.error()]
batch_process(events)
consumer.commit()
```

**Consumer group rebalancing**: when a consumer joins or leaves a group, Kafka reassigns partitions. During rebalancing, no consumption happens (pause). Minimize rebalancing by:
- Setting `session.timeout.ms` high enough that slow consumers don't get kicked
- Using static group membership (`group.instance.id`) — avoids rebalance on restart
- Using incremental cooperative rebalancing (`partition.assignment.strategy=CooperativeStickyAssignor`)

### Delivery Guarantees {#kafka-guarantees}

| Guarantee | Producer config | Consumer behaviour |
|---|---|---|
| **At-most-once** | `acks=0` | Commit offset before processing |
| **At-least-once** | `acks=all` | Commit offset after processing |
| **Exactly-once** | `enable.idempotence=True` + transactions | Transactional consumer + idempotent processing |

**Exactly-once** in practice (Kafka Streams / Flink handles this automatically):

```python
producer = Producer({
    "bootstrap.servers": "...",
    "enable.idempotence": True,
    "transactional.id": "my-producer-1",  # unique per producer instance
})

producer.init_transactions()

try:
    producer.begin_transaction()
    producer.produce("output-topic", key="k", value="v")
    producer.commit_transaction()
except Exception:
    producer.abort_transaction()
```

### Kafka Streams {#kafka-streams}

Kafka Streams is a Java library for stream processing that runs inside your application — no separate cluster needed.

```java
// Java — Kafka Streams word count
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> textLines = builder.stream("text-input");

KTable<String, Long> wordCounts = textLines
    .flatMapValues(line -> Arrays.asList(line.toLowerCase().split("\\W+")))
    .groupBy((key, word) -> word)
    .count();

wordCounts.toStream().to("word-counts-output",
    Produced.with(Serdes.String(), Serdes.Long()));

KafkaStreams streams = new KafkaStreams(builder.build(), config);
streams.start();
```

**Python alternative**: `faust` (Robinhood's Kafka Streams for Python):

```python
import faust

app = faust.App("word-count", broker="kafka://kafka:9092")

text_topic    = app.topic("text-input",     value_type=str)
counts_topic  = app.topic("word-counts",    value_type=int)
word_counts   = app.Table("word_counts",    default=int)

@app.agent(text_topic)
async def count_words(stream):
    async for line in stream:
        for word in line.lower().split():
            word_counts[word] += 1
            await counts_topic.send(key=word, value=word_counts[word])
```

### Kafka Pitfalls {#kafka-pitfalls}

| Pitfall | What happens | Fix |
|---|---|---|
| **Too few partitions** | Can't scale consumers past partition count | Plan ahead: partitions can't be decreased; start with 10–50 |
| **All messages same key** | All go to one partition → one consumer does all work | Use null key or distribute key space; avoid hot keys |
| **`auto.commit.enable=true` with slow processing** | Offset committed before processing done → data loss on crash | Set `enable.auto.commit=false`; commit after processing |
| **Consumer lag ignored** | Consumers fall behind → messages accumulate → disk full | Monitor consumer lag; alert if lag > N minutes |
| **Long message retention** | Disk cost grows unboundedly | Set `retention.ms` based on business need; use compacted topics for state |
| **No dead letter queue** | Poison pill message kills consumer loop | Catch exceptions; send unparseable messages to DLQ topic |
| **Rebalance during batch processing** | `max.poll.interval.ms` exceeded → consumer kicked → rebalance | Increase `max.poll.interval.ms`; process smaller batches |

## Apache Flink {#flink}

Flink is the most powerful open-source stream processor. Unlike Spark Streaming (micro-batch), Flink processes events one at a time with true sub-second latency.

```
Spark Structured Streaming:    Flink:
  trigger every N seconds       true event-by-event
  micro-batch model             continuous processing
  latency: seconds              latency: milliseconds
  easier API                    more expressive API
  better batch                  better streaming
```

**Key Flink concepts:**

- **Event time vs processing time**: Flink distinguishes when an event *happened* (event time) from when it *arrived* (processing time). Use event time for correct windowing over out-of-order streams.
- **Watermarks**: signals that say "all events with timestamp < W have arrived." Used to trigger window evaluation and handle late data.
- **State**: Flink maintains state per key, checkpointed to durable storage (S3, HDFS). Restores exactly-once on failure.
- **Savepoints**: manually triggered checkpoints for planned upgrades — stop, savepoint, upgrade code, restart from savepoint.

```python
# PyFlink example
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.table import StreamTableEnvironment

env = StreamExecutionEnvironment.get_execution_environment()
env.set_parallelism(4)
t_env = StreamTableEnvironment.create(env)

# Kafka source
t_env.execute_sql("""
    CREATE TABLE kafka_events (
        user_id    STRING,
        event      STRING,
        value      DOUBLE,
        ts         TIMESTAMP(3),
        WATERMARK FOR ts AS ts - INTERVAL '10' SECOND
    ) WITH (
        'connector' = 'kafka',
        'topic' = 'user-events',
        'properties.bootstrap.servers' = 'kafka:9092',
        'format' = 'json'
    )
""")

# Windowed aggregation (event-time window)
t_env.execute_sql("""
    CREATE TABLE results (
        window_start TIMESTAMP(3),
        window_end   TIMESTAMP(3),
        event        STRING,
        cnt          BIGINT,
        total_value  DOUBLE
    ) WITH (
        'connector' = 'jdbc',
        'url' = 'jdbc:postgresql://db:5432/analytics',
        'table-name' = 'event_windows'
    )
""")

t_env.execute_sql("""
    INSERT INTO results
    SELECT
        TUMBLE_START(ts, INTERVAL '5' MINUTE),
        TUMBLE_END(ts, INTERVAL '5' MINUTE),
        event,
        COUNT(*),
        SUM(value)
    FROM kafka_events
    GROUP BY TUMBLE(ts, INTERVAL '5' MINUTE), event
""")
```

**When to use Flink over Spark Streaming:**
- Need sub-second latency (Flink: ~ms, Spark: ~seconds)
- Complex event processing (CEP) — detect patterns across events
- Exactly-once with low latency
- Very large state (Flink's RocksDB state backend scales to TBs)

## Data Lake Architecture {#data-lake}

### Table Formats: Delta, Iceberg, Hudi {#table-formats}

Raw object storage (S3/GCS) has no ACID transactions, no schema enforcement, and no efficient updates. Open table formats add a **transaction log** on top of Parquet files to provide these guarantees.

```
Data Lake without table format:
  s3://bucket/events/
    part-00001.parquet   ← written by job A
    part-00002.parquet   ← written by job B simultaneously
    part-00001.parquet   ← job C overwrites? or appends?
  
  No consistency guarantee. Reader might see partial writes.
  Can't update or delete rows. Schema can drift silently.

Data Lake WITH Delta Lake:
  s3://bucket/events/
    _delta_log/
      00000.json   ← transaction: added part-00001.parquet, part-00002.parquet
      00001.json   ← transaction: deleted 500 rows matching user_id='u123'
      00002.json   ← transaction: schema changed, added column
    part-00001.parquet
    part-00002.parquet
    part-00003.parquet   ← written by update transaction
  
  ACID. Time travel. Schema enforcement. Efficient updates/deletes.
```

```python
# ── Delta Lake ─────────────────────────────────────────────────────────
# pip install delta-spark

spark = SparkSession.builder \
    .config("spark.jars.packages", "io.delta:delta-core_2.12:2.4.0") \
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension") \
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog") \
    .getOrCreate()

# Write Delta table
df.write.format("delta").mode("overwrite").save("s3://bucket/delta/events")

# ACID upsert (MERGE)
from delta.tables import DeltaTable
delta_table = DeltaTable.forPath(spark, "s3://bucket/delta/events")

delta_table.alias("target").merge(
    updates_df.alias("source"),
    "target.user_id = source.user_id AND target.date = source.date"
).whenMatchedUpdateAll() \
 .whenNotMatchedInsertAll() \
 .execute()

# Time travel
df_yesterday = spark.read.format("delta") \
    .option("timestampAsOf", "2024-01-14") \
    .load("s3://bucket/delta/events")

df_version = spark.read.format("delta") \
    .option("versionAsOf", 5) \
    .load("s3://bucket/delta/events")

# Show history
delta_table.history().show()

# Compact small files
delta_table.optimize().executeCompaction()

# Remove old versions (keep 7 days)
delta_table.vacuum(retentionHours=168)

# Schema evolution
df_with_new_col.write.format("delta") \
    .option("mergeSchema", "true") \
    .mode("append") \
    .save("s3://bucket/delta/events")

# Z-order: co-locate related data for fast filtering
delta_table.optimize().executeZOrderBy("user_id", "date")
```

**Delta vs Iceberg vs Hudi:**

| Feature | Delta Lake | Apache Iceberg | Apache Hudi |
|---|---|---|---|
| Backed by | Databricks / Linux Foundation | Netflix / Apache | Uber / Apache |
| ACID | ✓ | ✓ | ✓ |
| Time travel | ✓ | ✓ | ✓ |
| Schema evolution | ✓ | ✓ (richer) | ✓ |
| Row-level deletes | ✓ | ✓ | ✓ |
| Hidden partitioning | ✗ | ✓ | ✗ |
| Streaming upserts | Via merge | Via merge | Native (COW/MOR) |
| Best with | Spark/Databricks | Multi-engine (Spark/Flink/Trino) | Spark + frequent updates |
| Industry adoption | Very high | Growing fast | Common at Uber/scale |

**Iceberg's hidden partitioning** is particularly powerful — you partition by `months(ts)` but queries filter on `ts` directly (no need to know the partition scheme). Partition evolution without rewriting data.

### Lakehouse Pattern {#lakehouse}

```
Traditional Architecture (Lambda):
  ┌──────────────────────────────────────┐
  │  Batch layer: Spark → Data Warehouse │  accurate, slow
  │  Speed layer: Kafka → Redis/Cassandra│  fast, approximate
  │  Serving layer: query both, merge    │  complex
  └──────────────────────────────────────┘

Lakehouse (Kappa-like):
  ┌──────────────────────────────────────────────────────┐
  │  Object Storage (S3/GCS) + Table Format (Delta/Iceberg)│
  │                                                      │
  │  Ingest: Kafka → Spark Streaming → Delta             │
  │  Batch:  Spark → Delta (same table, MERGE)           │
  │  Query:  Databricks / Trino / Athena / BigQuery      │
  │          (all read same Delta/Iceberg tables)         │
  │                                                      │
  │  One source of truth. No synchronisation needed.     │
  └──────────────────────────────────────────────────────┘
```

**Bronze → Silver → Gold** (Medallion architecture):

```
Bronze (raw):   Exact copy of source. No transformations. Schema-on-read.
                Retention: 1–2 years. Used for reprocessing.

Silver (clean): Deduplicated, typed, validated. PII masked.
                Schema enforced. Partitioned by date.

Gold (curated): Business-level aggregations. Joined with dimensions.
                Optimised for analytics queries. Refreshed daily/hourly.

s3://bucket/
  bronze/events/         ← raw Kafka dump, Parquet
  silver/events/         ← cleaned, deduplicated Delta table
  gold/daily_user_stats/ ← aggregated Delta table, Z-ordered
```

## Batch vs Stream: When to Use What {#batch-vs-stream}

```
Batch processing:                    Stream processing:
  Process accumulated data at once     Process each event as it arrives
  High throughput                      Low latency
  Simple to reason about               Complex (state, watermarks, ordering)
  Errors reprocessable easily          Errors need careful handling
  
  Latency: minutes to hours            Latency: milliseconds to seconds
  
  Use when:                            Use when:
  ✓ Daily/hourly reports               ✓ Real-time dashboards
  ✓ ML feature pipelines               ✓ Fraud detection
  ✓ Data warehouse loads               ✓ Alerting / anomaly detection
  ✓ Large historical backfills         ✓ Personalisation (react to user action)
  ✓ Complex ML training                ✓ Event-driven microservices
```

**The practical rule**: start with batch. Add streaming only when latency genuinely matters for the use case. Streaming adds significant operational complexity for a latency benefit that many use cases don't need.

## Pipeline Patterns {#pipeline-patterns}

**ELT vs ETL:**

```
ETL (traditional):
  Source → Transform → Load to warehouse
  Transformation happens before storage
  Complex data pipelines, often fragile
  Good when: warehouse can't handle raw data; PII must be removed before storage

ELT (modern):
  Source → Load raw → Transform in warehouse (dbt/Spark SQL)
  Raw data always available for reprocessing
  Transformations are versioned SQL, easy to iterate
  Good when: warehouse is powerful enough (Snowflake, BigQuery, Databricks)
```

**Idempotent pipelines** — running a job twice gives the same result as running it once:

```python
# Non-idempotent (breaks on re-run):
df.write.mode("append").parquet("s3://bucket/output/")  # doubles data on re-run

# Idempotent:
df.write.mode("overwrite").parquet("s3://bucket/output/date=2024-01-15/")
# or with Delta:
delta_table.alias("t").merge(source.alias("s"), "t.id = s.id") \
    .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()
```

**Incremental processing with watermarks:**

```python
# Track last processed timestamp in a checkpoint table
checkpoint_df = spark.read.parquet("s3://bucket/checkpoints/last_run")
last_run = checkpoint_df.collect()[0]["max_timestamp"]

# Only read new data
new_data = spark.read.parquet("s3://bucket/events/") \
    .filter(F.col("timestamp") > last_run)

# Process new_data...
# Update checkpoint
new_max = new_data.agg(F.max("timestamp")).collect()[0][0]
spark.createDataFrame([{"max_timestamp": new_max}]) \
    .write.mode("overwrite").parquet("s3://bucket/checkpoints/last_run")
```

**Orchestration** — scheduling and dependency management:

| Tool | Model | Best for |
|---|---|---|
| **Apache Airflow** | Python DAGs, cron-scheduled | Complex pipelines with many dependencies |
| **Prefect** | Python tasks/flows, cloud-managed | Modern alternative to Airflow; easier testing |
| **Dagster** | Asset-centric, strongly typed | Data assets; great observability |
| **dbt** | SQL models, DAG of transformations | In-warehouse transformations |
| **AWS Step Functions** | Serverless state machine | AWS-native; Glue/Lambda orchestration |
| **Databricks Workflows** | Notebook/job clusters | Spark jobs on Databricks |
