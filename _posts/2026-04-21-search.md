## Overview
{: #overview}

Modern enterprise search is not a single algorithm — it is a pipeline of interdependent systems, each with its own failure modes and optimisation levers. At Microsoft Copilot Search scale, the system must retrieve across millions of documents in email, Teams chats, SharePoint, and external connectors, respect per-user ACLs, handle noisy heterogeneous content, and do this at low latency while producing results that ground Copilot answers faithfully.

    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--green">Grounding / Answer Generation — RAG with ranked chunks</span></li>
  </ol>

## Query Understanding
{: #query-understanding}

### Query Taxonomy
{: #query-types}

Not all queries are equal. Understanding the *type* of query determines how to rewrite, retrieve, and rank.

| Type | Example | Challenge |
|---|---|---|
| **Navigational** | "Q3 budget spreadsheet" | User wants a specific known document |
| **Informational** | "what is our PTO policy" | User wants an answer, not a document |
| **Transactional** | "find emails from John about project X" | Structured filters + relevance |
| **Ambiguous** | "performance review" | Could be their own review, the process, or a template |
| **Conversational** | "what did we discuss last Tuesday" | Requires session context and entity resolution |
| **Cross-lingual** | Query in Spanish, docs in English | Multilingual embedding alignment needed |

> **Interview question:** How would you detect whether a query is navigational vs informational?
>
> **Answer:** Classic approach: train a classifier on query features — query length, presence of proper nouns, presence of file extensions, named entities, past click behaviour. Short queries with proper nouns tend to be navigational. Modern approach: use an LLM to classify intent zero-shot or few-shot as part of the query understanding pipeline. For enterprise search, implicit signals (user clicked and opened a specific document vs read a paragraph) are strong supervision for this classification.

### Query Rewriting & Expansion
{: #query-rewriting}

Raw user queries are often too short, ambiguous, or use different vocabulary from the indexed documents. Rewriting bridges this gap.

<div class="post-flow post-flow--horizontal" role="group" aria-label="Query rewriting strategies">
  <ol class="post-flow__list post-flow__list--row">
    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--muted">Spell correction</span></li>
    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--muted">Synonym expansion</span></li>
    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--blue">HyDE</span></li>
    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--blue">LLM rewrite</span></li>
    <li class="post-flow__step"><span class="post-flow__bar post-flow__bar--green">Multi-query</span></li>
  </ol>
</div>

**Spell correction & normalisation**: stemming, lemmatisation, abbreviation expansion (e.g., "Q3" → "third quarter 2024"), acronym resolution using a domain-specific dictionary.

**Query expansion (pseudo-relevance feedback, PRF)**: take top-k results from an initial retrieval, extract key terms, and add them to the query. Classic Rocchio algorithm; modern version uses a neural model to identify useful expansion terms.

**HyDE (Hypothetical Document Embeddings)** [(Gao et al., 2022)](https://arxiv.org/abs/2212.10496): prompt an LLM to generate a *hypothetical answer document* for the query. Embed that document and use it as the query vector. The idea: a generated answer is in the same vocabulary and style as real indexed documents, so its embedding aligns better with the document embedding space than the short query embedding does.

```python
def hyde_query_vector(query, llm, embed_fn, n_hypothetical=5):
    """
    Generate n hypothetical answers, embed each, return their mean.
    """
    hypotheticals = [
        llm(f"Write a short document that answers: {query}")
        for _ in range(n_hypothetical)
    ]
    vecs = embed_fn(hypotheticals)          # (n, D)
    return vecs.mean(axis=0)               # (D,) — averaged hypothesis vector
```

**LLM query rewriting**: prompt an LLM to produce a cleaner, more specific query. Especially useful for conversational search where the current query is underspecified without the session history.

```python
REWRITE_PROMPT = """
Rewrite the following search query to be more specific and self-contained,
resolving any pronouns or references from the conversation history.

History: {history}
Query: {query}
Rewritten query:"""
```

**Multi-query**: generate K diverse paraphrases of the query, retrieve candidates for each, then fuse results. Increases recall at the cost of latency and compute.

> **Interview question:** What are the failure modes of HyDE?
>
> **Answer:** HyDE assumes the LLM can generate a relevant hypothetical document for any query. For factual enterprise queries ("what did Alice say in the design review"), the LLM has no access to the actual content, so it generates a plausible-sounding but completely wrong document. The embedding of a wrong document can point in an arbitrary direction and actually hurt recall compared to embedding the original query. HyDE works best for generic factual questions where the answer structure is predictable. It should be gated: only apply HyDE when the query is informational and the LLM confidence is high, or when offline evaluation shows it improves NDCG.

### Intent & Entity Recognition
{: #intent-entities}

Enterprise queries are rich with entities: person names, project names, document titles, dates, and org-specific terminology.

**Named Entity Recognition (NER)** identifies spans: `[John Smith]_PERSON`, `[Project Phoenix]_PROJECT`, `[Q3 2024]_DATE`. These entities can be used to:
- Hard-filter the candidate set (only emails involving John Smith)
- Boost documents that contain exact entity matches
- Route to specialised indexes (people search, calendar search)

**Entity linking** resolves "John" to a canonical user ID in the directory. Critical for enterprise: "John" may resolve to 50 different employees; user's org chart, recent email threads, and meeting history provide context for disambiguation.

**Slot filling for structured queries**: detect filter intent from queries like "emails from Sarah last week about budget". Extract: `sender=Sarah`, `date_range=last_week`, `topic=budget`. Execute as a structured filter + semantic search on `topic`.

---

### Personalisation & Context
{: #personalisation}

Enterprise search is inherently personal. The same query "project status" means completely different things to different users based on their role, team, and recent activity.

**Signals for personalisation:**
- Recent documents opened, edited, shared
- Meeting attendees and recurring contacts
- Project and team memberships from the directory
- Recent queries and click-through patterns
- Time of day / day of week

**Implementation approaches:**
1. **Query-side enrichment**: append implicit context to the query before retrieval. E.g., embed `"project status [user: PM, team: Copilot Search, recent_project: Phoenix]"` instead of bare `"project status"`.
2. **Document-side personalisation score**: learn a user-specific relevance signal and combine it with the base ranking score at reranking time.
3. **Two-tower personalised retrieval**: encode user context in the query tower; the document tower is user-agnostic. Fast because document embeddings are precomputed.

## Retrieval Algorithms
{: #retrieval}

### BM25 & Sparse Retrieval
{: #bm25}

> **Paper:** [Okapi BM25 — Robertson & Zaragoza, 2009 (survey)](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf) · [WAND: Efficient Top-K Document Retrieval — Broder et al., 2003](https://www.cs.cmu.edu/~quora/research/papers/2003_wand_krovetz.pdf)

BM25 is the foundation of all serious retrieval systems. It remains competitive with dense retrieval on keyword-heavy queries and is used in virtually every production hybrid system.

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

where $$f(t,d)$$ is term frequency, $$|d|$$ is document length, $$k_1 \in [1.2, 2.0]$$ controls TF saturation, $$b = 0.75$$ controls length normalisation.

**Inverted index**: BM25 is implemented on an inverted index — a mapping from each term to a sorted posting list of `(doc_id, tf)` pairs. For a query with $$k$$ terms, retrieval is $$O(k \cdot \bar{L})$$ where $$\bar{L}$$ is the average posting list length. Fast impact-ordered traversal with WAND (Weak AND) or BMW (Block-Max WAND) prunes most documents without scoring them, achieving sub-millisecond latency even on billion-document corpora.

**Enterprise BM25 extensions:**
- **Field-weighted BM25**: title, subject, and sender fields get higher weight than body.
- **Freshness decay**: multiply BM25 score by $$e^{-\lambda \cdot \text{age\_days}}$$ to favour recent documents.
- **Anchor text**: for SharePoint pages, anchor text from linking pages is a strong relevance signal (mirrors PageRank-era web search).

### Dense / Bi-Encoder Retrieval
{: #dense}

> **Paper:** [Dense Passage Retrieval for Open-Domain QA — Karpukhin et al., EMNLP 2020](https://arxiv.org/abs/2004.04906) · [E5: Text Embeddings by Weakly-Supervised Contrastive Pre-training — Wang et al., 2022](https://arxiv.org/abs/2212.03533) · [BGE M3-Embedding — Chen et al., 2024](https://arxiv.org/abs/2402.03216)

Bi-encoder models (DPR, E5, BGE, GTE, Nomic) encode query and document independently into a shared embedding space. Retrieval is maximum inner product search (MIPS).

$$\text{score}(q, d) = \text{enc}_Q(q) \cdot \text{enc}_D(d)^\top$$

**Training**: contrastive learning with in-batch negatives + hard negatives mined from BM25 top results that are not relevant. Loss: InfoNCE.

**Fine-tuning for enterprise**: pre-trained bi-encoders trained on MS-MARCO or Natural Questions transfer poorly to enterprise content because:
- Enterprise vocabulary (internal project names, product codenames, org acronyms) is out-of-distribution
- Relevance criteria differ: in web search, freshness matters less; in enterprise, the 2-day-old email is often more relevant than the 2-year-old wiki
- Document structure differs: emails have headers, meetings have transcripts, SharePoint has hierarchical site structure

**Adaptation strategies:**
- **Domain-adaptive pre-training (DAPT)**: continue MLM pre-training on the enterprise corpus before fine-tuning for retrieval
- **In-domain contrastive fine-tuning**: use implicit feedback (clicks, opens, forwards) as weak supervision for positive pairs
- **Instruction-tuned embeddings** (E5-Mistral, GTE-Qwen): prepend task-specific instructions (`"Represent this enterprise email for retrieval"`); dramatically reduces domain gap

### Hybrid Retrieval & RRF
{: #hybrid}

> **Paper:** [Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods — Cormack, Clarke & Buettcher, SIGIR 2009](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)

Neither BM25 nor dense retrieval dominates across all query types. Hybrid combines both.

**Reciprocal Rank Fusion (RRF)** — the canonical fusion method:

$$\text{RRF}(d) = \sum_{r \in \text{rankings}} \frac{1}{k + \text{rank}_r(d)}$$

where $$k = 60$$ is a smoothing constant. RRF is robust, parameter-free, and handles score scale mismatch between BM25 and cosine similarity automatically.

```python
def rrf(rankings: list[list[int]], k: int = 60) -> list[tuple[int, float]]:
    """
    rankings: list of ranked doc-id lists (best first)
    Returns merged ranking sorted by RRF score.
    """
    scores: dict[int, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

**Linear score fusion** (alternative): $$s = \alpha \cdot s_\text{BM25\_norm} + (1-\alpha) \cdot s_\text{dense}$$. Requires normalising scores to the same scale (min-max or z-score per query). More tunable than RRF but sensitive to distribution shift.

> **Interview question:** When does BM25 beat dense retrieval and vice versa?
>
> **Answer:** BM25 wins on **exact-match queries** — product codes, file names, rare technical terms, proper nouns, and short precise queries. Dense retrieval beats BM25 on **semantic/paraphrase queries** — synonyms, cross-lingual queries, and queries that require understanding sentence-level meaning. The [BEIR benchmark (Thakur et al., 2021)](https://arxiv.org/abs/2104.08663) shows this clearly: BM25 is competitive or better on entity-heavy datasets (TREC-COVID, DBPedia) while dense retrieval wins on NQ and MSMARCO. In enterprise search, BM25 is particularly strong for navigational queries ("Q3 forecast Excel") while dense is stronger for informational ones ("how do I expense travel"). Hybrid consistently outperforms either alone across query type distributions.

### SPLADE & Learned Sparse
{: #splade}

> **Paper:** [SPLADE: Sparse Lexical and Expansion Model for First Stage Ranking — Formal et al., SIGIR 2021](https://arxiv.org/abs/2107.05720) · [SPLADE++: Efficient Neural Sparse Retrieval — Formal et al., 2022](https://arxiv.org/abs/2205.04733)

SPLADE (Sparse Lexical and Expansion model) learns a sparse, high-dimensional representation over the vocabulary. Unlike BM25, SPLADE can assign weight to terms not present in the original text — it performs implicit query/document expansion using BERT's masked language model head.

$$w_j = \log(1 + \text{ReLU}(\text{MLM\_head}(h_i)_j)) \quad \text{(max-pooled over tokens)}$$

The $$\log(1 + \text{ReLU}(\cdot))$$ activation encourages sparsity — most vocabulary dimensions get weight 0. The result is a BERT-enhanced inverted index that:
- Handles synonymy (BERT's MLM expands semantically related terms)
- Is compatible with standard inverted index infrastructure
- Achieves recall competitive with bi-encoders without ANN indexing

**SPLADE++** adds distillation from a cross-encoder teacher and FLOPS regularisation to control index size.

### ColBERT & Late Interaction
{: #colbert}

> **Paper:** [ColBERT: Efficient and Effective Passage Search via Contextualized Late Interaction — Khattab & Zaharia, SIGIR 2020](https://arxiv.org/abs/2004.12832) · [ColBERTv2: Effective and Efficient Retrieval via Lightweight Late Interaction — Santhanam et al., 2022](https://arxiv.org/abs/2112.01488)

ColBERT generates per-token embeddings for both query and document, then uses a MaxSim operator:

$$\text{score}(q, d) = \sum_{i \in \text{query\_tokens}} \max_{j \in \text{doc\_tokens}} \mathbf{e}_{q_i} \cdot \mathbf{e}_{d_j}^\top$$

This "late interaction" is more expressive than bi-encoder dot product (which compresses full document meaning into one vector) while being far cheaper than cross-encoder full attention (which requires the query and document to be jointly encoded).

**ColBERT v2** compresses token vectors to 16 bytes with residual compression (centroid + residual quantisation), making it practical for billion-scale retrieval. **PLAID** (Production-Level Approximate Interaction for DeFS) adds candidate generation + interaction pruning to make ColBERT deployable at Google/Microsoft scale.

## Vector Indexing Internals
{: #vector-indexing}

### The ANN Problem
{: #ann-problem}

Exact nearest neighbour search in $$d$$ dimensions requires $$O(N \cdot d)$$ time — infeasible for N = 100M documents and d = 768. Approximate Nearest Neighbour (ANN) algorithms trade a small amount of recall for orders-of-magnitude speedup. The core quality metric is **recall@K**: what fraction of the true top-K neighbours are in the returned set.

The **curse of dimensionality** makes intuition from low-dimensional spaces wrong: in 768 dimensions, random vectors are nearly orthogonal, so distance becomes less discriminative. Quantisation and hierarchical graphs exploit structure that exists despite high dimensionality.

> **Counter-intuition:** You might expect that higher-dimensional embeddings are *harder* to search because there are more directions to get lost in. In practice, semantic embedding spaces have *intrinsic dimensionality* much lower than 768 — most of the variance lies in a small subspace. ANN algorithms exploit this by partitioning or routing along the high-variance directions, ignoring the noisy low-variance ones. This is why IVF with 1024 centroids can achieve >95% recall even though theoretically it's only covering a tiny fraction of the 768-dimensional sphere.

---

### IVF — Inverted File Index
{: #ivf}

> **Paper:** [Billion-scale similarity search with GPUs — Johnson et al., 2017 (FAISS)](https://arxiv.org/abs/1702.08734)

IVF is the workhorse of large-scale ANN. It partitions the vector space into $$n_\text{list}$$ Voronoi cells using k-means clustering, then at query time only searches the $$n_\text{probe}$$ nearest cells.

**Intuition:** Think of it as a city map. You divide the city into postal districts (Voronoi cells). To find the nearest coffee shop to your location, you don't search all shops in the city — you search only the shops in your district and a few neighbouring districts. The k-means centroids are the "district centres"; the inverted lists are the shops per district.

**Counter-intuition:** You'd expect that searching more cells always improves recall monotonically. It does, but with diminishing returns — after probing ~5–10% of cells, you've already found ~99% of the true nearest neighbours. The remaining 1% are in cells whose centroids are far from the query but whose *actual members* happen to be close. These are called **boundary effects** — vectors that live near the Voronoi boundary between two cells. IVF-PQ mitigates this by also searching within each cell using compressed distances, but the fundamental boundary issue remains.

**Full algorithm:**

**Offline (index construction):**
1. Run k-means on all $$N$$ vectors with $$n_\text{list}$$ centroids. Typical: $$n_\text{list} = 4\sqrt{N}$$.
2. Assign each vector to its nearest centroid.
3. Store an inverted list per centroid: `centroid_id → [vec_id, vec_id, ...]`.
4. (Optional) Apply Product Quantisation to compress vectors within each list.

**Online (query):**
1. Compute distance from query $$q$$ to all $$n_\text{list}$$ centroids: $$O(n_\text{list} \cdot d)$$.
2. Select the $$n_\text{probe}$$ nearest centroids (typically $$n_\text{probe} \approx \sqrt{n_\text{list}}$$).
3. Exhaustively search all vectors in those $$n_\text{probe}$$ lists: $$O(n_\text{probe} \cdot \frac{N}{n_\text{list}} \cdot d)$$.
4. Return top-K by distance.

```python
import numpy as np

class IVF:
    def __init__(self, n_list: int, n_probe: int):
        self.n_list = n_list
        self.n_probe = n_probe
        self.centroids = None      # (n_list, D)
        self.lists = None          # list of arrays: each is (n_i, D) of assigned vectors
        self.list_ids = None       # list of arrays: each is (n_i,) of original ids

    def train(self, vectors: np.ndarray, n_iter: int = 25):
        """K-means clustering to find Voronoi centroids."""
        N, D = vectors.shape
        # Random initialisation
        idx = np.random.choice(N, self.n_list, replace=False)
        self.centroids = vectors[idx].copy()

        for _ in range(n_iter):
            # Assign each vector to nearest centroid.
            # Use identity ||x-c||^2 = ||x||^2 + ||c||^2 - 2 x·c
            # to avoid computing all pairwise differences (expensive).
            dists = (
                (vectors ** 2).sum(1, keepdims=True)     # (N, 1)
                + (self.centroids ** 2).sum(1)           # (n_list,)  broadcast
                - 2 * vectors @ self.centroids.T         # (N, n_list)
            )
            assignments = dists.argmin(axis=1)           # (N,)

            # Update: new centroid = mean of all assigned vectors
            new_centroids = np.zeros_like(self.centroids)
            counts = np.zeros(self.n_list)
            np.add.at(new_centroids, assignments, vectors)
            np.add.at(counts, assignments, 1)
            counts = np.maximum(counts, 1)
            self.centroids = new_centroids / counts[:, None]

        return assignments

    def add(self, vectors: np.ndarray, ids: np.ndarray, assignments: np.ndarray):
        """Populate inverted lists after training."""
        self.lists    = [[] for _ in range(self.n_list)]
        self.list_ids = [[] for _ in range(self.n_list)]
        for vec, vid, c in zip(vectors, ids, assignments):
            self.lists[c].append(vec)
            self.list_ids[c].append(vid)
        self.lists    = [np.array(lst) if lst else np.empty((0, vectors.shape[1]))
                         for lst in self.lists]
        self.list_ids = [np.array(lst) for lst in self.list_ids]

    def search(self, query: np.ndarray, k: int):
        """Search n_probe nearest cells, return top-k global ids and distances."""
        dists_to_centroids = ((self.centroids - query) ** 2).sum(axis=1)
        probe_cells = np.argsort(dists_to_centroids)[:self.n_probe]

        cand_vecs, cand_ids = [], []
        for cell in probe_cells:
            if len(self.lists[cell]) > 0:
                cand_vecs.append(self.lists[cell])
                cand_ids.append(self.list_ids[cell])

        if not cand_vecs:
            return np.array([]), np.array([])

        cand_vecs = np.concatenate(cand_vecs)   # (M, D)
        cand_ids  = np.concatenate(cand_ids)    # (M,)
        dists = ((cand_vecs - query) ** 2).sum(axis=1)
        top_k = np.argsort(dists)[:k]
        return cand_ids[top_k], dists[top_k]
```

**Tuning:**

| Parameter | Too low | Too high | Rule of thumb |
|---|---|---|---|
| $$n_\text{list}$$ | Lists too large, slow search | Centroids too sparse, low recall | $$4\sqrt{N}$$ |
| $$n_\text{probe}$$ | Miss boundary vectors, low recall | Search too many cells, slow | Start at $$\sqrt{n_\text{list}}$$, tune on recall curve |

- **IVF-PQ**: combine IVF with Product Quantisation to compress vectors from 3KB to 32 bytes. ADC (asymmetric distance computation) uses lookup tables — each distance is $$m$$ table lookups instead of $$d$$ multiplications. Standard production choice for 100M+ corpora.
- **IVF-HNSW**: index the centroids themselves with HNSW so centroid search is sub-linear. Useful when $$n_\text{list}$$ is ≥ 100K.

> **Interview question:** IVF assigns each vector to exactly one centroid. Why is this a problem and how do you fix it?
>
> **Answer:** A vector near the boundary of two Voronoi cells is assigned to one centroid but is close to vectors in the other cell. If the query lands in the other cell and you only probe that one cell, you miss this boundary vector entirely. Fix: (1) increase $$n_\text{probe}$$ to search more cells; (2) use **multi-index** (assign each vector to its 2 nearest centroids, paying 2× storage); (3) HNSW doesn't have this problem because it uses a graph — neighbours are explicit regardless of cell boundaries.

### HNSW — Hierarchical Navigable Small World
{: #hnsw}

> **Paper:** [Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs — Malkov & Yashunin, 2018](https://arxiv.org/abs/1603.09320)

HNSW builds a multi-layer proximity graph where each node is a vector. Search is a greedy graph traversal. It is the **most widely used ANN algorithm** in production (Elasticsearch, Weaviate, Qdrant, Pinecone, pgvector all use it by default).

**Background — Six Degrees of Separation:** The "small world" phenomenon: in any large social network, any two people are connected through ~6 hops. Random graphs exhibit this property — short average path length combined with high local clustering. Watts & Strogatz (1998) formalised this. **Navigable** small world means you can find the short path *greedily* — each hop takes you measurably closer to the target.

**The core problem NSW solves:** Build a proximity graph where each node connects to its $$M$$ approximate nearest neighbours. Greedy search from a random entry node converges to the query's neighbourhood in $$O(\log N)$$ hops. BUT: if you start far from the query, early hops are in the wrong region and greedy search gets stuck in local optima — "false terminators" that are locally but not globally nearest.

**HNSW's fix — exponential hierarchy:** Inspired by skip lists. Add multiple layers above layer 0:
- Layer 0: all $$N$$ nodes, density $$M$$ edges per node
- Layer 1: random $$N/e$$ nodes (expected), same local edges
- Layer 2: random $$N/e^2$$ nodes, ...

Search starts at the top layer (few nodes, coarse map of the space) and descends. By the time you reach layer 0, you're already in the right neighbourhood, so greedy search doesn't get stuck.

**Intuition for why the random sampling works:** At the top layer you have a coarse grid of "long-range" nodes. Greedy search at the top quickly homes in on the right region of the embedding space. You descend, each layer adding more local detail. It's like zooming in on a map — first continent, then country, then city, then street.

**Counter-intuition:** You might think the randomness of which nodes appear at higher layers would hurt quality. In fact it's essential — if you deterministically chose the "most central" nodes for higher layers, you'd create a hierarchical clustering that greedy search could get stuck in. The randomness ensures higher-layer nodes are spread uniformly across the space, providing good global coverage. This is the same reason random projections work better than PCA for hashing.

**Full HNSW construction algorithm:**

```
INSERT(q, hnsw):

Step 1: Sample insertion layer
  L = floor(-ln(uniform(0,1)) * m_L)
  where m_L = 1/ln(M)
  → Geometric distribution: P(node reaches layer l) = e^{-l/m_L}
  → Most nodes (fraction 1 - 1/e ≈ 63%) stay at layer 0
  → ~37% reach layer 1, ~14% reach layer 2, etc.

Step 2: Find entry point for insertion
  ep = hnsw.entry_point   (the single global entry, always at max layer)

Step 3: Descend from max_layer to L+1 (traversal only, ef=1)
  For each layer l from max_layer down to L+1:
    ep = SEARCH_LAYER(q, ep, ef=1, layer=l).closest_result
  → We are just homing in on the right neighbourhood,
    not yet inserting. ef=1 = greedy single-path descent.

Step 4: Insert at layers L down to 0 (ef = ef_construction)
  For each layer l from L down to 0:
    # Find ef_construction nearest neighbours at this layer
    candidates = SEARCH_LAYER(q, ep, ef=ef_construction, layer=l)
    
    # SELECT_NEIGHBOURS heuristic (not just M nearest!):
    #   Sort candidates by distance to q.
    #   Keep a candidate c only if it is closer to q than
    #   to any already-selected neighbour.
    #   This ensures edges point in diverse directions.
    neighbours = SELECT_NEIGHBOURS_HEURISTIC(q, candidates, M)
    
    # Add bidirectional edges
    for n in neighbours:
      add edge q <-> n at layer l
    
    # Prune over-connected nodes
    for n in neighbours:
      if degree(n, layer=l) > M_max:   # M_max = M (l>0), 2M (l=0)
        prune n's edges with SELECT_NEIGHBOURS to M_max

Step 5: Update global entry point if L > current max layer
```

**Full HNSW search algorithm:**

```
SEARCH(q, k, ef):

Step 1: ep = hnsw.entry_point

Step 2: Greedy descent through upper layers (ef=1)
  For l from max_layer down to 1:
    ep = SEARCH_LAYER(q, ep, ef=1, layer=l).best

Step 3: Beam search at layer 0 (ef >= k)
  results = SEARCH_LAYER(q, ep, ef=ef, layer=0)

Step 4: Return top-k from results

SEARCH_LAYER(q, ep, ef, layer):
  W = {ep}          # result set (max-heap by dist, size ef)
  C = {ep}          # candidate set (min-heap by dist — explore closest first)
  visited = {ep}
  
  while C not empty:
    c = C.pop_min()         # closest candidate not yet fully explored
    worst_in_W = W.peek_max()
    
    # Early termination: if the closest unexplored candidate is
    # farther than our current worst result, no new node can improve W
    if dist(q, c) > dist(q, worst_in_W):
      break
    
    for neighbour n of c at this layer:
      if n not in visited:
        visited.add(n)
        if dist(q, n) < dist(q, W.peek_max()) or |W| < ef:
          C.push(n)
          W.push(n)
          if |W| > ef:
            W.pop_max()   # evict farthest — keep W size = ef
  
  return W
```

**SELECT\_NEIGHBOURS\_HEURISTIC (the key to graph quality):**

```
# Naive: just take M closest candidates. Problem: all M edges cluster
# in one direction, leaving the rest of the space unreachable.
#
# Heuristic: greedily select candidates that are diverse.
# A candidate c is added only if it is closer to q than to
# any already-selected neighbour r:
#   dist(q, c) < dist(r, c) for all already-selected r

def select_neighbours_heuristic(q, candidates, M, dist_fn):
    candidates = sorted(candidates, key=lambda c: dist_fn(q, c))
    selected = []
    for c in candidates:
        if len(selected) >= M:
            break
        # Keep c only if it is closer to q than to any selected neighbour
        if all(dist_fn(q, c) < dist_fn(r, c) for r in selected):
            selected.append(c)
    return selected
```

**Why SELECT\_NEIGHBOURS\_HEURISTIC matters:** Without it, all $$M$$ edges from a new node point to the same tight cluster. The graph becomes a series of isolated cliques — no long-range edges to bridge distant regions. The heuristic forces edges to cover diverse directions, ensuring the "small world" property is preserved.

**Key parameters:**

| Parameter | Effect | Typical value |
|---|---|---|
| **M** | Edges per node. Higher → recall ↑, memory ↑ | 16 (balanced), 64 (high recall) |
| **M\_max0** | Max edges at layer 0 | 2M (denser bottom layer) |
| **ef\_construction** | Beam width during build. Higher → graph quality ↑, build time ↑ | 100–500 |
| **ef** (search) | Beam width during query. Higher → recall ↑, latency ↑ | Tune for target recall |
| **m\_L** | Level multiplier = 1/ln(M) | Auto from M |

**Memory**: each node stores its vectors (768 × 4 = 3KB) + edge lists (~M × 4 bytes per layer). For N=10M, M=16: ~50GB RAM for vectors + ~2GB for graph = feasible on one server.

**HNSW limitations:**
- **No efficient deletion**: nodes can be marked as deleted (tombstoned) but accumulate and hurt recall. Periodic index rebuilds are needed.
- **Memory-resident**: all vectors + graph must fit in RAM. 1B vectors = ~3TB — requires sharding.
- **Slow construction**: $$O(N \log N)$$ with large constant. Building 100M vectors takes hours.
- **Not streaming-friendly**: inserting a node modifies many existing nodes' edge lists (bidirectional edges + pruning), making parallelism hard.

> **Interview question:** Why does HNSW use an exponential distribution for layer assignment instead of, say, a uniform distribution?
>
> **Answer:** An exponential (geometric) distribution ensures the expected number of nodes at layer $$l$$ decreases by factor $$e$$ per layer, mirroring the structure of a skip list. This gives $$O(\log N)$$ nodes at the top layer and $$O(1)$$ expected levels in total. With a uniform distribution, many nodes would reach high layers, making the upper layers too dense — they would no longer provide the global shortcut property. The exponential distribution is the unique distribution for which the "memoryless property" holds: the number of remaining levels to add is independent of how many you've already added. This makes the level assignment truly random and avoids correlations between node insertion order and layer assignment.

### ScaNN — Anisotropic Quantisation
{: #scann}

> **Paper:** [Accelerating Large-Scale Inference with Anisotropic Vector Quantization — Guo et al., NeurIPS 2020](https://arxiv.org/abs/1908.10396)

ScaNN introduces **anisotropic vector quantisation**: instead of minimising reconstruction error uniformly, it minimises error in the *direction that matters for MIPS* — the parallel component of the error (which directly affects dot product) is penalised more than the perpendicular component.

**Intuition:** Imagine approximating a document vector $$x$$ with a codeword $$\hat{x}$$. Standard PQ treats all approximation errors equally — it's like trying to reproduce a painting perfectly. But for ranking, you only care about the *dot product* with the query $$q$$. Errors perpendicular to $$q$$ don't affect $$q \cdot x$$ at all. ScaNN is like saying: "be as accurate as possible along the direction the query is pointing, and be sloppy elsewhere."

**Counter-intuition:** This seems query-dependent — you'd need to quantise differently for every query. ScaNN avoids this: it computes the anisotropic objective averaged over a distribution of queries during offline training. The resulting codebooks are query-agnostic but optimised for the *distribution* of queries likely to be seen.

**Standard PQ** minimises $$\|x - \hat{x}\|^2$$ — treats all error directions equally.

**ScaNN** minimises a weighted error:
$$\ell(x, \hat{x}) = \|x_\perp - \hat{x}_\perp\|^2 + t \cdot \|x_\parallel - \hat{x}_\parallel\|^2 \quad t \gg 1$$

where $$x_\parallel$$ is the component parallel to the query direction and $$x_\perp$$ is perpendicular. Errors in $$x_\parallel$$ affect ranking; errors in $$x_\perp$$ don't. ScaNN achieves 10× better recall at a given quantisation bitwidth compared to standard PQ.

**ScaNN pipeline:**
1. **Tree (IVF-style partitioning)**: partition corpus into clusters
2. **Anisotropic quantisation**: compress vectors within clusters using the AQ objective
3. **Asymmetric scoring**: at query time, compare the full-precision query against compressed document vectors using pre-computed lookup tables

ScaNN powers Google Search's embedding-based retrieval and holds state-of-the-art positions on the [ANN benchmarks leaderboard](https://ann-benchmarks.com).

### Product Quantisation
{: #pq}

> **Paper:** [Product Quantization for Nearest Neighbor Search — Jégou, Douze & Schmid, TPAMI 2011](https://lear.inrialpes.fr/pubs/2011/JDS11/jegou_searching_with_quantization.pdf)

PQ compresses vectors from $$d$$ floats (e.g., 768 × 4 = 3072 bytes) to $$m$$ bytes by splitting the vector into $$m$$ sub-vectors of dimension $$d/m$$ and quantising each independently with a codebook of 256 codewords.

**Intuition:** A 768-dimensional vector is too high-dimensional to quantise as a whole — you'd need $$256^{768}$$ codewords for perfect reconstruction. PQ solves this by divide-and-conquer: split the vector into 96 independent 8-dimensional sub-vectors, and quantise each with 256 codewords. Total codebook: $$96 \times 256 = 24{,}576$$ codewords instead of $$256^{768}$$. The independence assumption is the key approximation — if sub-vectors are truly independent, PQ is optimal. In practice embedding dimensions are correlated (use OPQ / rotation to decorrelate first).

**Counter-intuition:** You might expect that compressing a 3KB vector to 96 bytes (32× compression) would catastrophically hurt distance estimates. In practice, with $$m=96$$ sub-spaces and 256 codewords each, the quantisation error is small enough that the *ranking* of neighbours is mostly preserved — even if absolute distances are off. This is because ranking only requires the *relative ordering* of dot products, which is more robust to uniform quantisation noise than the absolute values.

**Construction:**
1. (Optional) OPQ: rotate vectors to decorrelate dimensions before splitting
2. Split all vectors into $$m$$ sub-vectors: $$x = [x^{(1)}, \ldots, x^{(m)}]$$, each of dimension $$d/m$$
3. For each sub-space $$i$$: run k-means with 256 centroids → codebook $$C^{(i)} \in \mathbb{R}^{256 \times d/m}$$
4. Encode vector $$x$$ as $$m$$ bytes: $$\text{code}(x) = [\text{argmin}_{c} \|x^{(1)} - c\|, \ldots, \text{argmin}_{c} \|x^{(m)} - c\|]$$

**Query-time (asymmetric distance computation, ADC):**
1. For each sub-space $$i$$: compute distance from query sub-vector $$q^{(i)}$$ to all 256 codewords → lookup table $$T^{(i)} \in \mathbb{R}^{256}$$ ($$m \times 256$$ total operations)
2. Approximate distance for document $$x$$: $$\hat{d}(q, x) = \sum_{i=1}^{m} T^{(i)}[\text{code}^{(i)}(x)]$$ — $$m$$ table lookups, not $$d$$ multiply-adds

**Compression ratio**: 768d float32 → 96 bytes (m=96, d/m=8) → **32× compression**. IVF-PQ96 stores 96 bytes per document rather than 3KB, enabling billion-scale search in RAM. Distance computation: 96 table lookups vs 768 multiplications — ~8× faster per distance calculation.

### DiskANN
{: #diskann}

> **Paper:** [DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node — Subramanya et al., NeurIPS 2019](https://proceedings.neurips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html)

DiskANN enables billion-scale ANN on a single server with SSD storage — most vectors live on disk, only a small working set is in RAM.

**Key insight**: SSDs can serve 1M random reads/sec with ~100μs latency. If the graph traversal requires only a small number of SSD reads per hop, the total latency budget is achievable even for disk-resident graphs.

**Intuition:** HNSW is fast but needs everything in RAM. DiskANN makes a clever trade: keep PQ-compressed vectors in RAM (tiny — 96 bytes instead of 3KB), use them for fast candidate filtering, and only load full-precision vectors from SSD for the final scoring step. This way, the fast path (filtering) is RAM-resident; only the slow path (re-scoring) hits disk.

**Counter-intuition:** You'd expect disk-based ANN to be much slower than RAM-based. The key insight is that search only needs $$O(\log N)$$ hops, so the number of SSD reads is logarithmic, not linear. For N=1B, that's ~30 reads × 100μs = 3ms disk time, which fits in a 10ms latency budget. Compare to IVF-PQ which needs $$N/n_\text{list}$$ sequential in-RAM reads per probed cell — also manageable but with worse recall.

**Construction**: Build a **Vamana graph** (similar to HNSW but optimised for disk access patterns — wider out-degree, no layer hierarchy, single flat graph). Use PQ-compressed vectors in RAM for beam search to identify promising candidates, then load full-precision vectors from SSD for re-scoring.

**Search**:
1. PQ in-RAM scan: use compressed vectors for fast initial candidate scoring (cache-friendly)
2. Beam search: expand candidates using SSD-resident graph edges (~30 SSD reads total)
3. Final re-ranking: load full-precision vectors for top candidates from SSD

DiskANN powers Bing's vector search infrastructure, handling trillion-scale indexes. The OSS version supports real-time index updates via **FreshDiskANN** — a streaming variant that maintains graph consistency under concurrent inserts and deletes.

| IVF-Flat | 90–99% | 5K–50K | High | Hard | Medium scale, good recall |

**Production choice heuristics:**
- **< 10M vectors, latency critical**: HNSW (Qdrant, Weaviate)

> **Interview question:** Why can't you just use HNSW for billion-scale enterprise search?
>
> **Answer:** HNSW requires all vectors in RAM. At 1B documents × 768d × 4 bytes = 3TB of RAM — prohibitively expensive. Additionally, HNSW deletes are expensive (no efficient online deletion — you accumulate tombstones or rebuild). Enterprise corpora have high churn: emails are sent, documents are updated, permissions change. DiskANN solves the memory problem with SSD storage; SPANN (hierarchical HNSW+IVF) adds efficient updates. In practice, production systems shard the index: each shard fits in RAM, and queries fan out to all shards in parallel.

## Reranking
{: #reranking}

### Cross-Encoder Rerankers
{: #cross-encoder}

Cross-encoders jointly encode (query, document) pairs through a transformer, producing a fine-grained relevance score. Unlike bi-encoders, they use full cross-attention between query and document tokens — no information bottleneck.

```python
# Bi-encoder: independent encoding
score = embed(query) · embed(doc)   # fast but lossy

# Cross-encoder: joint encoding
score = BERT([CLS] query [SEP] doc [SEP])[CLS_logit]   # slow but accurate
```

**Latency vs quality tradeoff**: cross-encoder inference is $$O(T_q \cdot T_d)$$ in attention complexity. At 512 token input, reranking 1000 candidates × 100ms each = 100 seconds. In practice: run on top-100 candidates from bi-encoder retrieval, with batch inference on GPU (50ms for 100 pairs).

**Popular models**: ms-marco-MiniLM-L-6 (fast, 6 layers), BGE-reranker-large (high quality), Cohere Rerank v3 (API).

**Distilled rerankers**: distil the cross-encoder teacher into a smaller model (4 layers, 128d hidden) for sub-10ms reranking. Quality degradation is small for top-20 precision.

---

### Listwise Reranking
{: #listwise}

Standard cross-encoders score each document independently (**pointwise**). **Listwise** rerankers score a document *relative to the other candidates*, capturing which document best satisfies the query given what else is available.

**RankLLaMA / RankGPT**: prompt an LLM with the full ranked list and ask it to re-order. Expensive but state-of-the-art for precision-critical tasks (legal search, medical).

**PairwiseRank (sliding window)**: compare adjacent pairs in the current ranking and swap if needed. Repeat with window sliding. $$O(N \log N)$$ pairwise comparisons.

**FIRST (Flashrank Instruction-tuned Reranker)**: a small (8B) instruction-tuned model that takes the top-20 list and outputs a re-ordered list in one forward pass. Fast enough for production with dynamic batching.

---

### Score Fusion
{: #fusion}

When multiple signals contribute to final ranking (BM25, dense score, freshness, personalisation, reranker score), they must be combined:

| Method | Formula | When to use |
|---|---|---|
| Linear interpolation | $$s = \sum_i w_i s_i$$ | Interpretable; requires score normalisation |
| RRF | $$s = \sum_i 1/(k + r_i)$$ | Rank-based; scale-invariant |
| LambdaMART | Gradient-boosted trees on features | Many signals, offline-tunable |
| Neural re-scoring | Feed all signals into a small MLP | End-to-end trainable with click feedback |

**LambdaMART** [(Burges, 2010)](https://www.microsoft.com/en-us/research/publication/from-ranknet-to-lambdarank-to-lambdamart-an-overview/) (LightGBM/XGBoost on ranking features) is the production standard for learning-to-rank (LTR). Features: BM25 score, dense score, reranker score, query-document overlap, document freshness, user personalisation signals, document type. Trained on human relevance judgements or implicit click feedback. Used in Bing, Google, LinkedIn, Airbnb.

## Enterprise Search Challenges
{: #enterprise}

### ACL & Security Trimming
{: #acl}

Enterprise search must never return documents a user cannot access. This is a **hard constraint**, not a ranking signal.

**Approaches:**

**Pre-filtering (index-time ACL)**: store ACL metadata alongside each document in the index. At query time, add ACL filters before or during ANN search. Problem: ACL updates require index updates; large orgs have billions of ACL changes per day.

**Post-filtering (retrieval-time ACL)**: retrieve top-K, then filter out inaccessible documents. Requires over-retrieving (top-10K instead of top-10) to ensure K accessible results survive. Works well when the accessible fraction is high.

**ACL-aware ANN**: encode user context in the query vector and train an ACL-aware embedding that naturally de-ranks inaccessible content. Not used for hard security guarantees (a model might make mistakes), but useful for soft personalisation.

**Microsoft Graph architecture**: Copilot Search resolves permissions via the Microsoft Graph API, which centralises all M365 ACLs. The search engine pre-fetches the user's accessible item IDs for the most common content types and uses them as a hard filter. For connectors (external data sources), the connector framework exposes a permission model that is integrated into the same filter layer.

### Freshness & Staleness
{: #freshness}

In enterprise search, a 3-day-old email about a decision is often more relevant than a 3-year-old wiki that discusses the same topic. Freshness must be incorporated into ranking.

**Signals:**
- **Created at / modified at**: direct timestamps from metadata
- **Access recency**: when was this document last opened by anyone on the team
- **Conversation activity**: number of replies, reactions in the last N days
- **Reference freshness**: how recently other documents link to this one

**Decay functions:**
$$\text{freshness}(t) = e^{-\lambda \cdot (T_\text{now} - T_\text{doc})}$$

The decay constant $$\lambda$$ is tuned per content type: emails decay faster (hours–days), wiki pages slower (months), reference documents (policies, procedures) may not decay at all.

**Index freshness**: the index must reflect the live corpus. Microsoft uses a near-real-time indexing pipeline where new documents are indexed within seconds, leveraging Azure Event Grid push notifications from SharePoint and Exchange.

### Deduplication & Near-Duplicate Detection
{: #dedup}

Enterprise content is highly redundant:
- Same document attached to 50 emails
- Draft v1, v2, v3, final, final-FINAL of the same document
- Meeting notes summarised in multiple formats
- Connector ingestion double-indexing documents from overlapping sources

**Exact deduplication**: hash the document (SHA-256 of content) and de-duplicate at index time.

**Jaccard similarity — the foundation:**

Before MinHash, you need Jaccard. Given two sets $$A$$ and $$B$$ (e.g., sets of word n-grams):

$$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$

Jaccard = 0 means no overlap; Jaccard = 1 means identical. For near-duplicate detection, documents with $$J > 0.8$$ are near-duplicates.

**Intuition:** Strip two documents down to their 3-gram shingles (e.g., "the cat sat" → {`the_cat_sat`, `cat_sat_on`, `sat_on_the`, ...}). Two paraphrase rewrites of the same paragraph will share most shingles even if sentence order changes slightly. Jaccard on shingle sets is a robust near-duplicate signal.

**Counter-intuition:** Jaccard works on *sets* not *bags* — it ignores how often a shingle appears. Two documents where one repeats the same sentence 100 times look identical to a document with that sentence once. For deduplication this is usually fine (repetition doesn't change the document's identity), but for plagiarism detection it may matter.

**Problem:** Computing exact Jaccard requires materialising $$A \cup B$$ — $$O(\vert A \vert + \vert B \vert)$$ per pair. For 10M documents, $$O(N^2)$$ pairs is infeasible. **MinHash** solves this with a compact sketch.

---

**MinHash — the probabilistic sketch:**

> **Paper:** [On the Resemblance and Containment of Documents — Broder, 1997](https://www.cs.princeton.edu/courses/archive/spr04/cos598B/bib/broder97resemblance.pdf) *(the original MinHash paper)*

**Key theorem:** for a random hash function $$h$$ (equivalently, a random permutation of the element space),

$$
\Pr\!\left[\min_{x \in A} h(x) = \min_{x \in B} h(x)\right] = J(A, B)
$$

**Why this is true:** consider all elements in $$A \cup B$$, and let

$$
x^* = \arg\min_{x \in A \cup B} h(x)
$$

be the globally minimum element under the random permutation. Since every element of $$A \cup B$$ is equally likely to be the minimum,

$$
\Pr[x^* \in A \cap B] = \frac{|A \cap B|}{|A \cup B|} = J(A, B)
$$

If $$x^* \in A \cap B$$, then both sets have the same minimum hash value:

$$
\min_{x \in A} h(x) = \min_{x \in B} h(x) = h(x^*)
$$

If instead $$x^* \in A \setminus B$$ or $$x^* \in B \setminus A$$, then the minima are different. So the probability that the minima match is exactly the Jaccard similarity.

**MinHash signature:** Use $$k$$ independent hash functions $$h_1, \ldots, h_k$$. For document $$D$$:
$$\text{sig}(D) = [\min_{x \in D} h_1(x),\ \min_{x \in D} h_2(x),\ \ldots,\ \min_{x \in D} h_k(x)]$$

**Estimating Jaccard from signatures:**
$$\hat{J}(A, B) = \frac{1}{k} \sum_{i=1}^{k} \mathbf{1}[\text{sig}(A)_i = \text{sig}(B)_i]$$

The variance of this estimator is $$J(1-J)/k$$. With $$k=128$$: standard deviation ≈ 0.04 at $$J=0.5$$. Accurate enough for deduplication.

**Practical implementation** — the "one hash + XOR" trick avoids $$k$$ expensive hash computations:

```python
import hashlib
import numpy as np

def minhash_signature(tokens: list[str], n_hashes: int = 128) -> np.ndarray:
    """
    Compute MinHash signature for a document.
    
    The theoretical construction uses n_hashes independent random permutations
    of the token space. In practice: use one base hash per token, then mix
    with n_hashes different seeds using fast integer XOR.
    
    Returns: (n_hashes,) array of minimum hash values — the signature.
    """
    # Use large prime multipliers as pseudo-random seeds
    # (simulates independent hash functions via universal hashing)
    rng = np.random.default_rng(42)
    a = rng.integers(1, 2**31, size=n_hashes)  # odd multipliers
    b = rng.integers(0, 2**31, size=n_hashes)  # offsets
    PRIME = (1 << 31) - 1  # Mersenne prime

    sig = np.full(n_hashes, np.inf)

    for token in tokens:
        # Base hash: single SHA256 call per token
        base = int(hashlib.sha256(token.encode()).hexdigest()[:8], 16)
        # Simulate k permutations via universal hash family h_i(x) = (a_i * x + b_i) mod p
        h = (a * base + b) % PRIME   # (n_hashes,)
        sig = np.minimum(sig, h)

    return sig.astype(np.int64)


def jaccard_from_minhash(sig1: np.ndarray, sig2: np.ndarray) -> float:
    """Unbiased Jaccard estimate: fraction of MinHash positions that agree."""
    return float((sig1 == sig2).mean())


def shingle(text: str, k: int = 3) -> set:
    """
    k-shingle (k-gram) tokenisation.
    'the cat sat' with k=2 → {'the_cat', 'cat_sat', 'sat_on', ...}
    Using word-level shingles is more robust to minor edits than char-level.
    """
    words = text.lower().split()
    return set("_".join(words[i:i+k]) for i in range(len(words) - k + 1))
```

**LSH (Locality-Sensitive Hashing) — scaling to millions of pairs:**

> **Paper:** [Mining of Massive Datasets, Chapter 3 — Leskovec, Rajaraman & Ullman](http://www.mmds.org/) *(the canonical LSH reference)*

Computing $$\hat{J}$$ for all $$O(N^2)$$ document pairs is infeasible. LSH uses the MinHash signature to **bucket candidate pairs** — only pairs that share a bucket need full Jaccard computation.

**LSH banding trick:**

Split the $$k$$-row signature into $$b$$ bands of $$r$$ rows each ($$k = b \times r$$).

For each band $$i$$, hash the $$r$$ values together → bucket ID. Two documents are **candidate duplicates** if they share at least one band's bucket.

```python
def lsh_candidates(
    signatures: dict[int, np.ndarray],   # doc_id → signature (k,)
    b: int,    # number of bands
    r: int,    # rows per band (k = b * r)
) -> set[tuple[int, int]]:
    """
    Return all (doc_a, doc_b) candidate pairs that share at least one band bucket.
    Expected false negative rate: (1 - J^r)^b
    Expected false positive rate: (1 - (1 - J^r)^b) for non-duplicates
    """
    from collections import defaultdict
    candidates = set()

    for band_idx in range(b):
        buckets = defaultdict(list)
        for doc_id, sig in signatures.items():
            band = tuple(sig[band_idx * r : (band_idx + 1) * r])
            buckets[band].append(doc_id)

        # Any bucket with >1 document is a candidate pair
        for bucket_docs in buckets.values():
            if len(bucket_docs) > 1:
                for i in range(len(bucket_docs)):
                    for j in range(i + 1, len(bucket_docs)):
                        candidates.add((bucket_docs[i], bucket_docs[j]))

    return candidates
```

**The S-curve analysis — how to choose b and r:**

The probability that two documents with Jaccard $$J$$ become candidates is:

$$P(\text{candidate} \mid J) = 1 - (1 - J^r)^b$$

This is an S-shaped curve (sigmoid-like) with the transition threshold at $$J^* \approx (1/b)^{1/r}$$.

```
J < J*: low probability of being a candidate → few false positives
J > J*: high probability of being a candidate → few false negatives
```

**Choosing b and r:**
- **Target threshold $$J^* = 0.8$$** (near-duplicates): choose $$b=20, r=5$$ → $$J^* = (1/20)^{1/5} \approx 0.55$$... let's tune more carefully.
- For $$J^* = 0.8$$: use $$b=20, r=6$$ ($$k=120$$) → $$J^* \approx (1/20)^{1/6} \approx 0.65$$. OR $$b=10, r=8$$ → $$J^* \approx (1/10)^{1/8} \approx 0.75$$. Plot the curve and pick based on your false positive budget.

```python
import numpy as np
import matplotlib.pyplot as plt  # for illustration only

def lsh_prob(J, b, r):
    return 1 - (1 - J**r)**b

# b=20, r=5: threshold ~0.47 — too low, many false positives
# b=10, r=8: threshold ~0.75 — tighter, fewer false positives
# b=5, r=20: threshold ~0.88 — very tight, misses some near-dups
```

**Counter-intuition:** Increasing $$b$$ (more bands) *lowers* the threshold — it's *easier* to find candidates, so you get more recall but more false positives. Increasing $$r$$ (more rows per band) *raises* the threshold — harder to match, fewer candidates, fewer false positives but more false negatives. This is the opposite of what you'd intuitively expect from "more bands = stricter".

**Full deduplication pipeline:**

```python
def deduplicate_corpus(
    docs: dict[int, str],
    jaccard_threshold: float = 0.8,
    n_hashes: int = 128,
    b: int = 16,    # k = b * r = 128
    r: int = 8,
) -> list[set[int]]:
    """
    Returns clusters of near-duplicate doc ids.
    Complexity: O(N * k) for signatures + O(N * b) for LSH bucketing
    vs O(N^2 * k) for brute-force.
    """
    # Step 1: Compute MinHash signatures
    sigs = {}
    for doc_id, text in docs.items():
        tokens = shingle(text, k=3)
        sigs[doc_id] = minhash_signature(list(tokens), n_hashes=n_hashes)

    # Step 2: LSH to find candidate pairs
    candidate_pairs = lsh_candidates(sigs, b=b, r=r)

    # Step 3: Verify candidates with exact Jaccard (on shingled sets)
    dup_pairs = set()
    shingles = {doc_id: shingle(text, k=3) for doc_id, text in docs.items()}
    for a, b_ in candidate_pairs:
        A, B = shingles[a], shingles[b_]
        j = len(A & B) / len(A | B) if A | B else 0.0
        if j >= jaccard_threshold:
            dup_pairs.add((a, b_))

    # Step 4: Union-Find to cluster duplicates
    parent = {doc_id: doc_id for doc_id in docs}

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x

    def union(x, y):
        parent[find(x)] = find(y)

    for a, b_ in dup_pairs:
        union(a, b_)

    clusters = {}
    for doc_id in docs:
        root = find(doc_id)
        clusters.setdefault(root, set()).add(doc_id)

    return list(clusters.values())
```

**Semantic deduplication** (complement to MinHash): embed documents, cluster by cosine similarity > threshold. Useful for paraphrased duplicates (meeting transcript + summary). MinHash is cheap and handles surface-level near-duplicates; semantic clustering catches semantic duplicates. Run MinHash first at scale, then semantic clustering on the survivors for a two-stage pipeline.

## Evaluation & Experimentation

### Offline Metrics
{: #offline-metrics}

**Precision@K**: fraction of top-K returned results that are relevant. Intuitive but doesn't reward ranking within the top-K.

**Recall@K**: fraction of all relevant documents that appear in top-K. Critical for RAG: if the relevant chunk isn't retrieved, the answer will be wrong regardless of how good the generator is.

**Mean Reciprocal Rank (MRR)**: for each query, take the reciprocal of the rank of the first relevant document, then average across queries.

$$
\text{MRR} = \frac{1}{|Q|} \sum_q \frac{1}{\text{rank}_{q,1}}
$$

Here, $\text{rank}_{q,1}$ is the rank of the first relevant document for query $q$. MRR rewards finding *any* relevant document high in the list, so it is especially useful for navigational queries.

**NDCG@K** (Normalised Discounted Cumulative Gain): graded relevance metric — a document rated 3 (highly relevant) contributes more than one rated 1 (marginally relevant). Discounts lower ranks logarithmically.

$$\text{DCG@K} = \sum_{i=1}^{K} \frac{2^{r_i} - 1}{\log_2(i+1)} \qquad \text{NDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}}$$

where IDCG is the ideal DCG achieved by a perfect ranking. NDCG@10 is the standard metric for information retrieval benchmarks (TREC, BEIR, MTEB).

```python
import numpy as np

def ndcg_at_k(relevances: list[int], k: int) -> float:
    """
    relevances: list of graded relevance scores for returned documents
                in rank order (best first). 0 = not relevant.
    """
    relevances = np.array(relevances[:k], dtype=float)
    gains = (2 ** relevances - 1) / np.log2(np.arange(2, len(relevances) + 2))
    dcg = gains.sum()

    # Ideal: sort relevances descending
    ideal = np.sort(relevances)[::-1]
    ideal_gains = (2 ** ideal - 1) / np.log2(np.arange(2, len(ideal) + 2))
    idcg = ideal_gains.sum()

    return float(dcg / idcg) if idcg > 0 else 0.0

def mean_reciprocal_rank(results: list[list[bool]]) -> float:
    """results: list of queries, each a list of booleans (relevant=True)."""
    rr = []
    for query_results in results:
        for rank, rel in enumerate(query_results, 1):
            if rel:
                rr.append(1.0 / rank)
                break
        else:
            rr.append(0.0)
    return float(np.mean(rr))

def recall_at_k(retrieved: list[int], relevant: set[int], k: int) -> float:
    """retrieved: doc ids in rank order. relevant: set of all relevant doc ids."""
    top_k = set(retrieved[:k])
    return len(top_k & relevant) / max(len(relevant), 1)
```

**Enterprise-specific metrics:**
- **Permission-filtered recall**: recall computed only on documents the user can access. Critical because a high raw recall that includes inaccessible documents is misleading.
- **Source diversity**: fraction of results from different content sources (email, SharePoint, Teams). A good enterprise search should not return 10 email threads when the answer is in a SharePoint document.
- **Answer groundability**: given the top-K retrieved chunks, what fraction of a grounded answer can be attributed to the retrieved content? Measured by an LLM judge or passage-level annotation.

### LLM-as-Judge
{: #llm-judge}

Human annotation is expensive and slow. LLM-as-judge uses a capable LLM (GPT-4o, Claude 3.5) as an automated relevance assessor.

```python
RELEVANCE_PROMPT = """
You are a relevance assessor for an enterprise search system.

Query: {query}
Document: {document}

Rate the relevance of this document to the query on a scale of 0–3:
0 = Not relevant
1 = Marginally relevant (tangentially related)
2 = Relevant (addresses the query but not perfectly)
3 = Highly relevant (directly and completely addresses the query)

Respond with only the integer score and a one-sentence justification.
Score:"""

def llm_relevance_judge(query: str, document: str, llm_fn) -> dict:
    prompt = RELEVANCE_PROMPT.format(query=query, document=document)
    response = llm_fn(prompt)
    # Parse score from first character
    score = int(response.strip()[0])
    justification = response.strip()[2:].strip()
    return {"score": score, "justification": justification}
```

**Consistency tricks:**
- **Chain-of-thought**: ask the LLM to reason before scoring — reduces variance
- **Reference-based**: provide a known-good reference document alongside the candidate and ask for comparative assessment
- **Multiple temperatures + majority vote**: run the judge 3× at T=0.3 and take the majority score
- **Calibration**: compare LLM judgements to human annotations on a held-out set; report Cohen's κ

**Limitations**: LLM judges have positional bias (prefer earlier documents in the prompt), verbosity bias (prefer longer, more detailed documents), and self-serving bias (prefer responses similar to their own training distribution). Mitigate with random position shuffling and calibration.

### Online Experiments
{: #online-experiments}

Offline metrics don't always predict online impact. A/B tests measure real user behaviour.

**Interleaving (preferred for search)**: rather than routing different users to A and B, interleave results from A and B in a single result list. Users click implicitly, revealing which results they found more useful. Interleaved experiments require 10–20× fewer users to reach statistical significance than standard A/B tests — critical at enterprise scale where the user population is much smaller than web search.

**Metrics:**
- **CTR (Click-through rate)**: fraction of queries that result in a click. Noisy signal — users may click anything at the top.
- **Abandonment rate**: fraction of queries with no action (no click, no dwell). High abandonment = poor results.
- **Task completion**: did the user find what they needed? Measured by post-query actions (forwarded email, opened file and stayed > 30s, referenced document in a reply).
- **Session success**: within a session (e.g., morning work block), what fraction of queries led to a successful task completion?
- **COEC (clicks per unique query)**: normalises CTR by query frequency — avoids high-volume head queries dominating the metric.

**Novelty effect handling**: users behave differently with new UI features (novelty effect inflates early CTR). Run experiments for at least 2 weeks and look for holdback metrics (long-term retained behaviour).

### Case Study 1 — Semantic Indexing at M365 Scale
{: #cs-semantic-indexing}

**Problem statement:** Microsoft 365 contains ~100 billion documents across Exchange, SharePoint, OneDrive, Teams, and external connectors. Every new or modified document must be semantically indexed (chunked, embedded, stored in a vector index) within minutes. The same index must serve retrieval for Copilot Chat, Copilot Search, and semantic search in Office apps — all with different recall/latency SLOs.

**Scale constraints:**
- ~10M document creates/updates per minute at peak (Monday morning)
- 768-dimensional embeddings — 3KB per document raw, ~3TB/billion docs
- Retrieval SLO: P95 < 30ms for the ANN lookup alone
- Index must support per-user ACL filtering without rebuilding per-user shards

**Key design decisions:**

| Decision | Option A | Option B (chosen) | Reason |
|---|---|---|---|
| **Index architecture** | One global index | Sharded per content type (email, doc, Teams) | Content-type-specific chunking and retrieval SLOs differ significantly |
| **Embedding model** | Single shared model | Task-specific model per content type | Emails and long documents have very different relevance signals |
| **Vector compression** | HNSW (full precision) | IVF-PQ96 (96 bytes/vec) | Memory: 100B docs × 3KB = 300TB vs 100B × 96B = 9.6TB — fits in reasonable RAM budget |
| **ACL enforcement** | Pre-filter in ANN (index per user) | Post-filter with over-retrieval | Per-user indexes are infeasible at M365 user count; post-filter with top-10K is practical |
| **Real-time updates** | Periodic rebuild (hours) | Streaming IVF variant + tombstoning | Minutes-latency indexing SLO requires streaming; periodic rebuild creates search gaps |

**Chunking strategy in detail:**

The chunking strategy is non-trivial because different content types have different natural units:

```python
CHUNK_STRATEGIES = {
    "email": {
        "method": "whole_document",     # emails are short; embed whole
        "max_tokens": 512,
        "fallback": "fixed_size_overlap",
    },
    "sharepoint_page": {
        "method": "semantic_sentence",  # split at H2/H3 boundaries + paragraph
        "max_tokens": 512,
        "overlap_tokens": 64,
    },
    "teams_thread": {
        "method": "conversation_window", # group messages by temporal proximity
        "window_minutes": 60,
        "max_tokens": 512,
    },
    "powerpoint": {
        "method": "per_slide",          # one chunk per slide
        "include_speaker_notes": True,
    },
    "pdf": {
        "method": "fixed_size_overlap",
        "max_tokens": 512,
        "overlap_tokens": 128,
    },
}
```

**The cold start problem:** When a new tenant onboards, their 5M existing documents must be indexed from scratch. Batch embedding throughput on a GPU cluster:

```
8 × A100 GPUs × 1000 embeddings/sec/GPU = 8000 embeddings/sec
5M docs × 10 chunks/doc = 50M chunks
50M / 8000 = 6250 sec ≈ 1.7 hours
```

Cold start is acceptable at ~2 hours. The streaming pipeline handles incremental updates thereafter.

**Failure modes and mitigations:**

| Failure | Symptom | Mitigation |
|---|---|---|
| Embedding service overload at Monday peak | Indexing lag grows; freshness SLO violated | Auto-scaling GPU pool + priority queue (recent edits > old documents) |
| IVF centroid skew | Popular content types (email) dominate centroids; SharePoint recall drops | Content-type-stratified k-means training for centroids |
| ACL store lag | User gains access to a document, still can't find it for 10 minutes | Two-phase ACL: coarse pre-filter from cached ACLs + real-time fine-filter via Microsoft Graph API at serve time |
| Chunk boundary artifacts | Relevant answer spans two chunks; neither chunk alone is retrievable | Overlapping chunks (stride < window); store parent document ID for answer extraction |

**Interview question:** You are designing the embedding update strategy. A document is edited — only 2 of its 20 chunks changed. Do you re-embed all 20 chunks or only the 2 changed ones?

> **Answer:** Re-embed only changed chunks, but this requires chunk-level change detection and chunk-level index updates. The implementation: (1) hash each chunk at index time; (2) on update, diff old vs new chunk hashes; (3) delete stale chunk vectors (tombstone), insert new ones. The benefit is 10× lower embedding compute at update time. The risk: if the embedding model is updated (fine-tuned), you need a full re-embed to keep the index consistent — you cannot mix old and new model embeddings in the same index. Mitigation: version the embedding model; schedule full re-embeds during model updates using the batch pipeline.

A distilled 4-layer BERT fine-tuned on labelled query intent data. Intent taxonomy:

| Intent | Example | Downstream effect |
|---|---|---|
| **Navigational** | "Q3 roadmap slide deck" | Boost exact-match, reduce recall threshold |
| **Informational** | "what is our parental leave policy" | Enable HyDE, boost semantic retrieval |
| **Transactional/filter** | "emails from Sarah last week about budget" | Extract structured filters, route to email index |
| **Conversational follow-up** | "what did she say about the deadline" | Requires session rewrite — entity "she" must be resolved |
| **People search** | "find John Smith's recent work" | Route to people + document index with person filter |

**Stage 3 — Entity extraction and linking (< 15ms):**

A span-level NER model identifies: `PERSON`, `PROJECT`, `DOCUMENT_TITLE`, `DATE`, `ORG_UNIT`. Entity linking maps spans to canonical IDs in the Microsoft Graph:

```python
# Entity linking example
query = "what did Alice say about Phoenix in the Monday meeting"

entities = {
    "Alice": {"type": "PERSON", "graph_id": "user:alice@contoso.com"},
    "Phoenix": {"type": "PROJECT", "graph_id": "project:phoenix-2024"},
    "Monday meeting": {"type": "MEETING", "graph_id": "event:cal-2026-04-21T09:00"},
}

# Structured filters derived from entities
filters = {
    "author_or_participant": "user:alice@contoso.com",
    "tagged_project": "project:phoenix-2024",
    "related_event": "event:cal-2026-04-21T09:00",
    "date_range": ("2026-04-21", "2026-04-21"),
}
```

**Stage 4 — Session-aware rewrite (< 30ms):**

For conversational follow-up queries, a small instruction-tuned LM (SLM — Phi-3-mini class) performs coreference resolution and session context injection. The SLM runs on-device or on a fast inference endpoint:

```python
REWRITE_PROMPT = """
You are an enterprise search assistant. Rewrite the user's latest query to be
fully self-contained, resolving all pronouns and references using the conversation history.
Output only the rewritten query — no explanation.

Conversation:
User: Show me the Phoenix project timeline
Copilot: [returned 3 documents about Project Phoenix]
User: What does she say about the Q3 deadline?

Rewritten query:"""

# Expected output:
# "What does Alice Chen say about the Q3 deadline in Project Phoenix?"
```

**Stage 5 — Embedding and HyDE (gated):**

- If intent = `INFORMATIONAL`: run HyDE (generate hypothetical document, embed it)
- Otherwise: embed the rewritten query directly
- For multilingual queries: use a multilingual embedding model (mE5, BGE-M3) that maps all languages to the same embedding space

**Latency accounting:**

| Stage | Latency | Model size | Hardware |
|---|---|---|---|
| Spell + normalise | 3ms | Rule-based + 10M param | CPU |
| Intent classify | 8ms | 22M param (4-layer BERT) | CPU |
| Entity extract + link | 12ms | 110M param NER + Graph API | CPU + Graph lookup |
| Session rewrite (SLM) | 45ms | 3.8B param (Phi-3-mini) | GPU (batched) |
| Embedding | 15ms | 560M param (E5-large) | GPU (batched) |
| **Total** | **83ms** | | |

Rewrite (45ms) is the bottleneck. Mitigation: (1) skip rewrite for single-turn queries (detected by intent classifier: `NAVIGATIONAL` and `INFORMATIONAL` rarely need rewrite); (2) cache rewrites for repeated session patterns; (3) use a smaller rewrite model (Phi-3-mini → TinyLlama at 1.1B) with 2× speedup at small quality cost.

**Interview question:** The entity linking stage calls the Microsoft Graph API for every query. This adds 10–20ms and creates a hard dependency on an external service. How do you make this resilient?

> **Answer:** Three-layer resilience: (1) **Cache** — maintain a per-user entity cache (people, projects, recently accessed documents) refreshed every 15 minutes. Most entity links hit the cache (< 1ms). (2) **Graceful degradation** — if the Graph API call times out, proceed without entity linking. The query still gets spell-corrected, intent-classified, and embedded. Retrieval is weaker but not broken. (3) **Circuit breaker** — if Graph API error rate exceeds 5% in a 10-second window, open the circuit: skip linking for all queries and alert the on-call engineer. Never block a search query on an auxiliary service being down. Measure impact: have offline metrics for "intent classify only" vs "full entity linking" so you know the quality degradation when the circuit is open.

### Case Study 3 — Freshness, ACL, and the Real-Time Update Problem
{: #cs-freshness-acl}

**Problem statement:** In a large enterprise, content changes at high frequency: documents are edited, emails arrive, meeting transcripts are generated, and permissions change (employee joins a team, leaves a project, is offboarded). The search index must stay consistent with both content freshness and ACL changes, in near-real-time, without degrading retrieval quality or violating security constraints.

**Requirements:**
- New/edited documents: indexed within **2 minutes** of the change (freshness SLO)
- ACL changes: enforced within **30 seconds** (security SLO — stricter than freshness)
- Deleted documents: removed from results within **30 seconds** (security SLO)
- No permission escalation: a user must never see a document they lost access to

**The ACL enforcement architecture:**

ACL enforcement is a **hard security constraint** — errors here are a data breach. The design splits into two tiers:

```
Tier 1 — Coarse pre-filter (fast, eventually consistent, ~30 sec lag):
  - ACL cache: doc_id → {allowed_group_ids} stored in Redis
  - Updated by ACL_UPDATE events via the event router
  - ANN search runs BEFORE this filter — retrieve top-10K candidates
  - Apply group-based filter: keep docs where user's group_ids ∩ doc.allowed_groups ≠ ∅
  - Latency: < 5ms (Redis lookup + bitset intersection)

Tier 2 — Fine-grained real-time check (slow, always current):
  - For top-20 results surviving Tier 1, call Microsoft Graph API
  - Verify per-document permission for the specific user
  - This is the authoritative check — Tier 1 can have false positives (shows docs user
    can't access yet due to cache lag) but NEVER false negatives (hides docs user can access)
  - Latency: 10–20ms for batch Graph API call
```

**Why two tiers?** The coarse filter removes 99%+ of inaccessible documents cheaply. The fine-grained check is the authoritative gate but is expensive — calling Graph for 10K candidates × every query is infeasible. Calling it for 20 candidates is affordable.

**ACL change propagation design:**

```python
class ACLEventHandler:
    """
    Handles ACL change events with strong consistency guarantees.
    
    Design invariant: if a user LOSES access to a document, the document
    must be removed from their results within 30 seconds.
    If a user GAINS access, it appears within 30 seconds (best effort,
    not security-critical).
    """

    def handle_permission_removed(self, user_id: str, doc_id: str):
        # 1. Immediately invalidate the per-user ACL cache entry
        self.acl_cache.delete(f"user:{user_id}:accessible_docs")
        # 2. Add doc to user's explicit deny list (fast lookup at query time)
        self.deny_list.add(user_id, doc_id, ttl=3600)
        # 3. Async: update the group-level ACL store
        self.acl_store.update_doc_permissions(doc_id)

    def handle_user_offboarded(self, user_id: str):
        # User leaving company — revoke all access immediately
        # 1. Purge user's entire ACL cache
        self.acl_cache.delete_all(f"user:{user_id}:*")
        # 2. Disable user's search access at the API gateway layer (< 1 sec)
        self.access_gateway.disable_user(user_id)
        # 3. Async cleanup of group memberships (eventual)
        self.group_store.remove_user_from_all_groups(user_id)
```

**The freshness vs index quality trade-off:**

Adding documents incrementally to an IVF-PQ index degrades index quality over time. When the IVF was trained, centroids represented the distribution of the corpus. New documents don't update the centroids — they just get assigned to the nearest existing centroid, which may be poor if the new document is semantically dissimilar to the training corpus.

| Approach | Freshness | Index quality | Cost |
|---|---|---|---|
| **Full periodic rebuild** | Hours lag | Best (centroids retrained) | High compute, gap period |
| **Streaming append** | Minutes lag | Degrades as corpus drifts | Low compute, continuous |
| **Hybrid: streaming + nightly rebuild** | Minutes lag | Good (rebuild corrects drift nightly) | Medium |
| **HNSW streaming insert** | Seconds lag | Good (graph self-corrects on insert) | High RAM (no compression) |

**Microsoft's likely approach:** Hybrid — streaming IVF append for freshness SLO, nightly centroid retraining + full reassignment to correct drift, with a shadow index swap (blue-green deployment of the index shard). The shadow index is built offline, validated against quality metrics, then swapped atomically.

**Tombstoning and the delete problem:**

Vector indexes don't support efficient deletes. Deleted documents accumulate as "tombstones" — they are marked deleted but still physically present in the index, wasting scan time. Mitigation:

```python
class TombstoneManager:
    def __init__(self, tombstone_threshold: float = 0.05):
        # If > 5% of vectors are tombstoned, trigger a compaction
        self.threshold = tombstone_threshold

    def should_compact(self, index_stats: dict) -> bool:
        tombstone_fraction = index_stats["tombstoned"] / index_stats["total"]
        return tombstone_fraction > self.threshold

    def compact(self, shard_id: str):
        """
        Rebuild shard without tombstoned vectors.
        During compaction: serve reads from the old shard, writes to new shard.
        On completion: atomic swap.
        """
        pass
```

At M365 scale, high-churn tenants (e.g., large financial firms with strict retention policies that delete emails after 90 days) can generate millions of deletes per day. A compaction schedule of "rebuild shard when > 5% tombstoned" keeps the overhead bounded.

**Interview question:** An employee is offboarded on Friday at 5pm. What are all the systems you need to update, in what order, and what is the blast radius if any one step fails?

> **Answer:** The order matters because security is asymmetric — false negatives (seeing data you shouldn't) are a breach; false positives (not seeing data you should) are merely inconvenient. (1) **API gateway — immediate** (< 1 second): disable the user's authentication token / AAD account. This is the authoritative cutoff — the user can no longer authenticate and therefore can no longer query at all. This is the safety backstop. (2) **ACL deny list — immediate** (< 1 second): add user to the search deny list so even if a stale token somehow gets through, search returns nothing. (3) **ACL cache invalidation — < 30 sec**: purge the user's group memberships from the ACL cache. Other users in the same groups are unaffected. (4) **Group membership update — < 2 min**: remove user from all Microsoft Graph groups. This updates the group-based ACL used by Tier 1 filtering. (5) **Index tombstoning — async**: no need to tombstone the user's *authored* documents (they remain accessible to others per ACL). If the user created private documents, those are covered by step 4 (user's private ACL group is removed). Blast radius: if step 1 fails but step 2 succeeds, the user is blocked at search. If both steps 1 and 2 fail but step 3 succeeds within 30 seconds, the user can query but all results are filtered. If step 3 fails, the Tier 2 real-time Graph check is the last line of defence. The system is designed so no single component failure causes a data breach — security is a chain of overlapping constraints, not a single gate.

**Consistency verification — the background reconciler:**

```python
def reconcile_shard(shard_id: str, source_of_truth_api):
    """
    Background job: compare search index state against source of truth.
    Run every 5 minutes per shard. Alert on discrepancies.
    """
    indexed_docs = index.list_doc_ids(shard_id)
    live_docs = source_of_truth_api.list_accessible_doc_ids(shard_id)

    # Documents in index but not in source of truth → stale, should be tombstoned
    stale = set(indexed_docs) - set(live_docs)
    for doc_id in stale:
        index.tombstone(doc_id)
        alert_if_sensitive(doc_id)  # flag if a deleted sensitive doc was still indexed

    # Documents in source of truth but not in index → missed during streaming ingest
    missing = set(live_docs) - set(indexed_docs)
    for doc_id in missing:
        reindex_queue.enqueue(doc_id)

    metrics.record("stale_docs", len(stale), shard=shard_id)
    metrics.record("missing_docs", len(missing), shard=shard_id)
```

**Key metrics to track in production:**

| Metric | Alert threshold | What it diagnoses |
|---|---|---|
| **Indexing lag P95** | > 5 min | Streaming pipeline backpressure or embedding service overload |
| **ACL propagation lag P99** | > 60 sec | ACL cache invalidation bug or Graph API degradation |
| **Tombstone fraction per shard** | > 5% | High-delete tenant needing compaction schedule adjustment |
| **Index-to-source-of-truth drift** | > 0.1% stale | Missed events in the streaming pipeline |
| **Reconciler false positive rate** | > 0.01% sensitive docs stale | Security incident — escalate immediately |
